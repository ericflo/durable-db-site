B2 publication protocol

Status: the shared B2/S3 publication implementation passed fault tests, bounded models, and an initial real-B2 integration test on 2026-11-08. Extended contention, scaling, and soak qualification continues.

Authority without a separate coordinator#

B2’s native bucket update accepts ifRevisionIs. Only the matching revision can update bucket metadata. Bucket listing returns revision and metadata. This supplies the publication point without conditional file overwrites.

The S3-compatible API carries immutable data pages, manifests, and B+tree directory pages. One durable-db-root bucket-info value identifies the directory root and its checksum. This respects B2’s metadata limits without imposing a small database-count ceiling. One dedicated bucket holds one cluster prefix. Unrelated metadata is preserved; lifecycle, public access, and retention fields are never changed by the adapter.

A writer uploads a fresh immutable manifest and proposal. Any replica servicing a write may combine up to 64 eligible proposals into one directory update, then replace bucket info with ifRevisionIs. Eligibility compares the original target pointer and global collection fence; rebuilding preserves all unrelated entries. Only final reachable changed index pages are uploaded. After submission, an unsuccessful response is uncertain because another replica may publish the proposal. Identical transaction receipts recover the result. PublicationCombining.tla models competing helpers, original unbatched publishers, stale observations, acknowledgement, and collection; negative controls expose fence, target, merge, and definite-abort mistakes. See the shared commit protocol.

Reads fetch bucket metadata, conditionally validate it with a fresh read fence, then traverse the directory and fetch the referenced manifest, verify its hash, and load immutable pages as needed. The successful conditional update is the read linearization point. If collection removes an old manifest in between, the whole manifest fetch restarts. Atomic revision checking is the safety assumption. Bucket listings may be stale: the read barrier retries a definite revision conflict and fails closed if it cannot validate within its bounded retry budget. It does not infer metadata freshness from file-visibility documentation. spec/ReadBarrier.tla models stale observations and conditional validation; its negative control returns stale data when validation is omitted.

Collection layers#

The engine’s original fence protects data pages. A second collector protects the immutable manifests: list candidates first, read the directory root, conditionally update bucket metadata with a fresh fence, then delete only listed manifests outside the protected tree. Index pages use a witness-key lookup to determine reachability without scanning the complete directory; see architecture. The same pass lists proposals before fencing and removes them only after the fence succeeds. A paused publisher or helper loses its revision comparison. Proven committed proposals may also be reclaimed through a bounded optional cleanup queue. The collector can die at any step without making its deletion authority transferable to a new attempt.

B2 always keeps file versions. Collection uses native b2_list_file_versions and b2_delete_file_version; S3 delete markers would leave the billed bytes behind. Duplicate versions caused by upload retries are deleted in bounded batches. No external retention/lifecycle policy may delete live database objects.

The same publication::Published code runs on S3; only wire operations differ. spec/Bucket.tla models two database slots, two pods, two attempts, and three bucket revision advances. It checks manifest reachability through crashes, partitions, stale writers, and concurrent collection. Its intentionally broken variant omits the fence and produces a missing-manifest counterexample. This complements the engine model; composition/refinement into Rust is not a completed proof.

Initial limits and performance#

The directory has no fixed database-count admission ceiling. Pages hold at most 64 entries/children and 64 KiB; point lookup and update traverse a logarithmic path. Listing and collection have bounded batch sizes. The root plus reserved maintenance fields fit the 9,000-byte metadata budget regardless of database count. Unrelated bucket metadata can still exhaust this budget; that configuration is rejected before uploads. Per-database data limits remain separate.

All metadata writes in a bucket still serialize. Scaling pods adds request concurrency, not unlimited write throughput for that bucket. A bounded group of reads shares one listing and conditional metadata validation, with membership sealed before validation begins. Each then traverses its selected directory and manifest. Immutable manifests and index pages share the bounded cache with data pages; mutable authority is never cached. Bounded publication groups share a root update across replicas. Independent publication partitions remain future work. Measure metadata throttling and latency before sizing a deployment; a large directory does not establish throughput for a large active tenant population.

Configuration#

export B2_APPLICATION_KEY_ID=...   # service-side credential, never a tenant token
export B2_APPLICATION_KEY=...
durable-db serve --listen 0.0.0.0:7654 --b2-bucket dedicated-private-bucket \
  --admin-key-file /run/secrets/admin.key

The key needs listBuckets, writeBuckets, readFiles, writeFiles, listFiles, and deleteFiles for this bucket. Native authorization refreshes after token expiration. Read-only bucket and version listings, including startup bucket discovery, retry selected transient HTTP statuses and transport failures at most three times within a ten-second deadline. Backoff starts at one second with jitter and honors numeric Retry-After; a requested wait beyond the remaining budget returns the error instead of retrying early. Invalid credentials and other permanent HTTP errors fail without status retries. Conditional publication errors remain uncertain and are not automatically retried as fresh comparisons. This follows Backblaze’s error-handling guidance while preserving the database’s stronger outcome contract. HTTP timeouts and upstream failure messages do not expose credentials to tenants. Startup checks that a stale revision is rejected.

A seven-day key restricted to the disposable test bucket successfully performed native revision publication and version deletion using B2 API v4. The account-wide operator key was used only to provision that bucket and workload key; it was not mounted into the database. Follow that separation in deployments. Check capabilities against the actual key type/API version rather than assuming every scoped key behaves identically.

Qualification evidence#

v0.7.0 can initialize fresh format-5 namespaces with cumulative upload admission. Live qualification found that B2 rejects more than ten bucket metadata entries. Its documented metadata contract also caps total value bytes at 10,000. The shared B2/S3 encoding packs control fields into a bounded document and reserves space for future fences and cursors. The directory remains an object-backed B+tree with no metadata-derived database-count cap.

The real-B2 test created a database, committed five revisions, recovered identical receipts, reclaimed old pages and manifests by file version, and reopened with a new client and empty cache. The format-3 suite also created 70 additional databases, crossed directory leaf splits, reclaimed obsolete index pages, paginated the directory, and reopened uncached. Both tests passed in 92 seconds. It uses DURABLE_DB_TEST_B2_BUCKET with cargo test --test b2_cloud -- --ignored --nocapture. Only use a dedicated test bucket; the test retains the final database for inspection.

Live API probes confirmed that a genuinely different stale bucket update returns 409 conflict, while an identical-metadata no-op may return success without advancing revision. Both provider connections now stamp every replacement with a fresh mutation identity in the existing reserved durable-db-probe field. This forces an actual conditional mutation even when the logical metadata is unchanged; callers cannot accidentally reuse a successful payload as a new validation. The shared startup probe still tests exclusion. Raw observations remain potentially stale, and a successful comparison alone does not grant ongoing serving authority. See the register contract and evidence. The directory encoding also exercises database names longer than B2’s metadata-key ceiling.

Long-running cloud contention, provider throttling, network fault injection, and CPU-triggered Kubernetes HPA/node-drain scenarios remain qualification work. The conditional read barrier is enabled unconditionally and must not be removed based only on optimistic benchmark results.

The first four-writer contention baseline failed: three operations exhausted retries with maintenance enabled. A diagnostic run without maintenance completed but still needed 59 conflict retries for 40 writes. See the full measurements and failed-run evidence. Shared publication progress and performance must be redesigned and qualified before production use.
