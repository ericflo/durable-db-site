B2 publication protocol

Status: implemented, modeled, and tested against an injected authority. Real B2 cloud qualification is pending dedicated test credentials. Do not equate the emulator with provider qualification.

Authority without a separate coordinator

B2’s native bucket update accepts ifRevisionIs. Only the matching revision can update bucket metadata. Bucket listing returns revision and metadata. This supplies the publication point without conditional file overwrites.

The S3-compatible API carries immutable data pages and immutable manifests. Each database gets one durable-db-head-<database> bucket-info entry containing a manifest name and SHA-256 digest. One dedicated bucket holds one cluster prefix. Unrelated metadata is preserved; lifecycle, public access, and retention fields are never changed by the adapter.

A writer reads the bucket revision, uploads a fresh manifest, then replaces bucket info with ifRevisionIs. A revision collision returns a conflict, including collisions caused by another database. A failed response may have committed; the engine’s transaction receipt recovers it. The adapter never republishes the same uploaded manifest against a later bucket revision.

Reads fetch bucket metadata and the referenced manifest, verify its hash, and load immutable pages as needed. If collection removes an old manifest in between, the whole manifest fetch restarts. The safety assumptions include atomic revision checking and fresh bucket metadata reads. Backblaze describes immediate visibility after file writes; metadata read semantics must also be qualified, rather than inferred from that file-write statement.

Two collection layers

The engine’s original fence protects data pages. A second collector protects the immutable manifests: list candidates first, read the complete current pointer set, conditionally update bucket metadata with a fresh fence, then delete only listed manifests outside the protected set. A paused publisher loses its revision comparison. The collector can die at any step without making its deletion authority transferable to a new attempt.

B2 always keeps file versions. Collection uses native b2_list_file_versions and b2_delete_file_version; S3 delete markers would leave the billed bytes behind. Duplicate versions caused by upload retries are deleted in bounded batches. No external retention/lifecycle policy may delete live database objects.

spec/Bucket.tla models two database slots, two pods, two attempts, and three bucket revision advances. It checks manifest reachability through crashes, partitions, stale writers, and concurrent collection. Its intentionally broken variant omits the fence and produces a missing-manifest counterexample. This complements the engine model; composition/refinement into Rust is not a completed proof.

Initial limits and performance

The flat metadata directory admits at most 32 databases and 9,000 serialized metadata bytes per bucket. An oversized update fails before uploading its manifest. This leaves room below B2’s metadata ceiling but unrelated metadata can reduce capacity. Database data limits remain separate.

All metadata writes in a bucket serialize. Scaling pods adds request concurrency, not unlimited write throughput for that bucket. Reads currently fetch both bucket metadata and immutable manifest; there is no stale manifest cache. Group commit and a partitioned multilevel directory are future format work, not current performance claims. Measure metadata throttling and latency before sizing a deployment. Provider upload/download rate limits are not a guarantee of metadata-update throughput.

Configuration

export B2_APPLICATION_KEY_ID=...   # service-side credential, never a tenant token
export B2_APPLICATION_KEY=...
durable-db serve --listen 0.0.0.0:7654 --b2-bucket dedicated-private-bucket \
  --admin-key-file /run/secrets/admin.key

The key needs listBuckets, writeBuckets, readFiles, writeFiles, listFiles, and deleteFiles for this bucket. Native authorization refreshes after token expiration. HTTP timeouts and upstream failure messages do not expose credentials to tenants. Startup checks that a stale revision is rejected.

Check the actual key’s scope: Backblaze’s capability documentation places restrictions on bucket-scoped writeBuckets, and authorization behavior depends on key type/API version. Do not assume an account-wide administrative key is necessary or that every scoped key works. Prefer a dedicated service account/key with the narrowest supported authority. The initial binary contains both the data and metadata clients; it does not implement a separate credential-isolation service.

Qualification still required

Dedicated-bucket cloud tests must exercise concurrent conditional updates, fresh reads, lost responses, version reclamation, cache-free reopen, throttling, and 1→N→1 pod changes. The existing platform credential could not create a disposable test bucket, so no production bucket was modified for testing. A metadata-read validation step may be necessary if the provider cannot establish fresh-read semantics.
