Production readiness

Release decision: not ready for production. v0.2.0 is an experimental release. The passing models, cloud tests, and 100,005-entry directory qualification establish a useful foundation. They do not establish safe public multitenancy, an operating envelope, disaster recovery, or a proof of the implementation.

The production release must retain one installable executable, directory-backed laptop development, and Kubernetes deployments that scale down to one node. Cluster data stays authoritative in B2 or S3 through one common storage algorithm, with bounded disposable caches and automatic maintenance. Performance, tenant protection and correctness are joint acceptance criteria.

This document tracks the gates for the first production release. A gate closes only with reproducible evidence tied to a commit and configuration. A design, a passing happy-path test, or a successful deployment is not sufficient. The verification record separates completed experiments from planned qualification.

Contract to qualify

The initial contract is atomic, revision-checked transactions and ordered scans within one database. Acknowledged writes must survive the loss of every API process and cache. Uncertain writes require identical retries; the recent receipt window is bounded. Cross-database transactions are outside this contract.

Current per-database limits are 256 MiB, 1,000,000 keys, and 2,048 pages, with smaller request and rewrite budgets. Large database counts and high active throughput are different requirements. The directory has been tested at 100,005 entries with sequential insertion, periodic collection, pagination, and an uncached reopen of every head. Concurrent HTTP provisioning and collection at that population, and a declared active workload, remain capacity gates. This synthetic-provider result is not a cloud capacity guarantee.

Total databases, active databases, peak read/write arrival rates, value sizes, contention, and p99 latency targets must be recorded before choosing a production topology. Measure B2 first, then AWS S3, using the same implementation and workload. Include physical object versions, provider calls, and bandwidth when estimating cost. A laptop-to-cloud measurement is not a regional Kubernetes SLO.

Backup retention and recovery objectives are not yet selected. A proposed starting point is 30-day point-in-time recovery with at most five minutes of backup lag. Recovery time must be measured against a declared database size and number of simultaneous restores. Neither this policy nor its cost is currently implemented or promised.

Implementation order

Current priority: replace the shared serving and durability path. The existing read barrier and shared publication path have not met the performance brief. Establish a safe ownership/read protocol and a measured batched durability path before expanding release or sustained-load qualification of a replacement.

  1. The native HTTP provider fixture passes B2 and versioned MinIO with a logical clock. Qualify runtime timing and switch the CLI once its contract is established. Complete the supported timing contract: the test binding now enforces guest sleep exclusion and passes no-sleep VM takeover, but hypervisor-host sleep and cross-host bounds remain unqualified. Then qualify elapsed time and restore/fork detection, the implemented renewal scheduler, election and placement, including a paused old owner that resumes after takeover. Keep the common B2/S3 storage algorithm.
  2. Measure warm reads, group commit and independent active databases through that serving path, including total-compute-loss recovery. Compare with the raw provider baseline. The public whole-database revision condition still limits same-database concurrency; exposing the existing key/range validator requires an explicit API contract.
  3. Integrate per-tenant physical admission and fair request/egress budgets. Do not refund rights that could still produce delayed uploads.
  4. Add compaction to the checkpoint writer, which now reuses unchanged tables and manifest nodes. Extend automatic reclamation beyond budget metadata to journals, tables and checkpoints with reader/backup retention, surviving complete compute/cache loss.
  5. Qualify Pi and general application workloads, mixed versions, provider failures, Kubernetes autoscaling, sustained load, disaster recovery and release artifacts. Resolve independent review findings before changing the production status.

Reproducible load baseline

scripts/benchmark-http.mjs creates synthetic databases on a disposable test deployment. It seeds one value per database, measures writes and reads with a configured number of workers, then verifies all seeded databases. The caller owns cleanup. Use scoped test-bucket credentials on the servers; the benchmark takes an administrator token from a file and does not print it.

node scripts/benchmark-http.mjs \
  --urls http://127.0.0.1:7654 \
  --token-file /path/to/test-admin-token \
  --databases 70 --workers 1,4 --operations 20 --value-bytes 1024 \
  --binary target/release/durable-db --output benchmark.json \
  --context 'Describe provider region, server placement, caches, concurrency, and maintenance'

Each worker owns one database so publication conflicts can retry the same request without recomputing application state. Ambiguous retries retain the exact ID, revision, and body. Reports include attempted/failed/not-started operations, HTTP statuses, full operation latency including backoff, successful latency separately, elapsed throughput, verification, and binary hash. A failed worker stops instead of issuing a new write ID after an unresolved outcome. The harness writes partial results and exits unsuccessfully on any failed phase or verification.

After a failed measured phase, the harness still checks final state, allowing an uncertain write to be either visible or absent at that read. This does not turn the timed-out operation into a success or establish that a delayed write can never arrive later. A lost-acknowledgement fixture checks failure accounting and identical retry bodies.

This is a closed-loop baseline: each worker waits for its preceding operation. It does not measure queue growth under a fixed arrival rate, establish a p99 SLO from a small sample, measure provider billing, or replace an open-loop overload test and soak campaign. The first B2 run failed its progress gate; that older serving path remains a baseline for the native replacement.
