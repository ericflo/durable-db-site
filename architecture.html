Understand

Architecture

Local serving uses the native journal, sorted-table index, checkpoints and collection described in the owned-partition design. A lifetime OS lock supplies single-host exclusion, so reads need no conditional publication or physical clock. The remaining sections describe the shared cloud engine; the native library now has clock-independent ownership and separate partition control records and owner forwarding, while automatic election/placement and the cloud CLI cutover remain open.

Authority and transaction boundary#

One database is one transaction boundary. Each database has a logical head named heads/<database>.json. In cluster mode, a shared immutable B+tree directory maps that head to an immutable manifests/<database>.<uuid> file. It lists immutable sorted pages, logical usage, quotas, recent request receipts, a collection cursor, a user revision, and a fresh fence identifier. Pages live under blocks/<database>.<uuid>; the delimiter cannot occur in a database identifier.

Reads validate the authoritative directory through a conditional read barrier, then fetch the selected immutable manifest. They load only the pages needed for exact keys or ordered scans. Immutable manifest, directory, and data-page bytes share the optional disk cache and bounded memory cache and are verified with SHA-256. Mutable authority observations and local heads are never cached. A fresh empty cache produces the same result. No full database hydration occurs at server startup.

The database directory is a multilevel B+tree. Within each individual database, the data-page index remains a bounded flat manifest of page ranges; lifting that per-database size limit is separate future work.

Commit protocol#

  1. Validate the directory, fetch the manifest, and retain its unique identity.
  2. Resolve an existing identical request receipt before checking the expected user revision.
  3. Check the revision, predicates, request bounds, and resulting logical quotas. Read and copy only touched pages; split them near 128 KiB.
  4. Upload replacement pages under globally fresh names. Finish every upload before publication.
  5. Recheck the database head identity and upload a fresh immutable manifest, then a bounded immutable proposal containing its expected old pointer, new pointer/digest, and original global collection fence. The manifest contains the incremented user revision and request receipt.
  6. A replica servicing a write lists at most 64 proposals and includes its own explicitly. It selects at most one eligible proposal per database, preserving the observed root’s unrelated entries, and uploads the changed directory pages. One conditional root replacement publishes the group.
  7. Acknowledge only with publication evidence: a successful CAS including this fresh manifest, or a genuine authority observation selecting it. Another replica may provide that publication after the origin disappears.

The conditional directory publication is each selected commit’s linearization point. Each proposal must match both its original database pointer and original global collection fence. A helper can retry at most eight conditional publications, rebuilding from a newly observed root and revalidating every selected proposal. A changed pointer or fence prevents reusing that proposal for another publication. The shared algorithm applies to B2 and S3.

Once proposal upload begins, absence from the current head does not prove an abort. Another replica may publish it later, or it may have committed and already been superseded. A changed fence, timeout, cancellation, or lost response therefore remains uncertain without publication evidence. Do not delete candidate pages or invent a rollback. Retry the identical request ID, expected revision, and body. Recent receipts recover the original result; an evicted receipt still cannot cause an identical request to reapply because its old expected revision fails. Request IDs must never be recycled for new work. Database creation currently has no idempotency key; uncertain create recovery is a separate lifecycle/API obligation.

Helpers fetch at most eight proposal/manifest objects concurrently and serialize directory staging within each process to bound transient memory. This local semaphore is an admission optimization, not a cluster authority. Bulk path copying stages at most 64 MiB and 1,600 intermediate pages, uploads only the final root’s new reachable pages with concurrency eight, and shares the existing cache budget. The 64-entry group limit does not limit the number of databases.

After proven publication, a bounded best-effort queue reclaims the selected proposal objects, with 128 waiting entries and eight concurrent deletions. Acknowledgement does not wait for cleanup. Dropped queues, provider failures, and disappearing processes leave work for the fenced collector; they never authorize deleting manifests or index pages.

Two transactions based on the same manifest cannot both publish. Cluster reads linearize at the directory read barrier. Together with expected-revision writes this gives database-scoped optimistic serializable transactions, provided clients recompute after conflicts and use one revision throughout a read/modify/write operation.

Collection without leases or clock assumptions#

Each server periodically lists a bounded page of databases. For each database it performs bounded compaction and collection. Concurrent collectors are allowed; they may duplicate work but cannot gain authority through their pod identities.

The collector finishes listing candidate objects before fetching the manifest. It then conditionally replaces that manifest with the same logical state and a new fence. Only after that succeeds does it delete candidates absent from the protected manifest.

Why a fence is necessary: a paused writer might have uploaded an object that is not yet referenced. Without the fence, a collector could delete it just before the writer publishes it. The fence invalidates every writer based on the prior manifest. A later writer can carry forward only currently referenced pages or newly named uploads that were not in the completed candidate listing. Retries must allocate fresh object names; content-addressed name reuse would invalidate this argument.

Collectors can stop at any instruction. A failed deletion leaves garbage for a later sweep. The collection cursor is stored with the fence and wraps after the end of the range. Objects created after a listing are collected in a later sweep. Successful writes never rely on a collector running.

A reader that loses a page of an old snapshot restarts the entire read from a fresh manifest. It returns a conflict if an explicit expected revision has moved. No partial scan or missing value is returned as a successful substitute.

A page-collection pass with no deletions and no cursor change does not publish a manifest; it needs no deletion fence. Automatic maintenance shares its initial manifest observation between compaction and this no-op check. If all listed candidates were live in that earlier snapshot and the cursor would stay unchanged, it may defer the pass without another read. A concurrent write can leave garbage for the next sweep, but this branch never deletes anything. Every actual deletion still reads after listing and conditionally publishes a fence. An idle database therefore needs one authoritative observation per maintenance pass instead of three.

Compaction replaces one adjacent pair of small pages without changing the logical revision. Its publication uses the same conditional-write discipline. Neither clocks nor Kubernetes termination hooks participate in data safety.

One publication implementation, small provider bindings#

Both B2 and S3 run publication::Published. It owns directory initialization and limits, the read barrier, immutable manifest publication, manifest collection, and retry rules. The engine above it owns page transactions and page collection. No provider selects a separate database algorithm.

Bucket metadata stores one durable-db-root reference. Database entries live in immutable indexes/<witness-database>.<uuid> objects, with at most 64 entries/children and 64 KiB per page. A branch records each child’s range, height, count, unique object name, and checksum. Insertion copies one path, splitting full pages. Lookup and update cost O(log N) index pages; listing is paginated without loading every database. Index and data pages share the configured cache budget. The metadata budget remains 9,000 bytes, including reserved root/cursor/fence space, independent of database count.

There is no fixed database-count admission ceiling. Counts use checked 64-bit arithmetic, and a height guard bounds corrupt input traversal. The directory qualification covers 100,005 entries in format 5, with sequential insertion, periodic collection, ordered pagination, and an uncached check of every head. The regular 10,005-entry regression also covers format 3. These synthetic-provider results do not establish cloud throughput or concurrent provisioning capacity. Publication format 3 rejects earlier experimental formats; budgeted formats 4 and 5 have their own incompatible envelopes. There is no in-place migration yet.

Directory collection lists at most 128 candidates in each of the manifest, index, and proposal namespaces before conditionally fencing the root. The fence invalidates every listed proposal, allowing its removal even if a helper retained its bytes. Manifest filenames identify their database, so one lookup determines whether a manifest is current. Each index filename embeds its original first database key as a witness. A still-reachable immutable subtree still contains that key; looking it up from the protected root must visit that subtree. This makes each candidate’s reachability check logarithmic, including when old nodes are reused under new parents. Missing index pages cause an error/restart, never a conclusion that a candidate is garbage. Concurrent collection can remove an old reader’s path, so reads and listings restart as a whole.

Directory.tla checks the witness reachability lemma over bounded immutable trees, including subtree reuse. Bucket.tla checks conditional publication and collection fencing at the abstract reference-set layer. Their composition into the tree implementation remains an explicit proof obligation.

A raw directory observation may be stale. The common read barrier conditionally publishes the unchanged root pointer with a new unique fence. Only success permits a read to use that snapshot. Each process groups at most 64 waiting observations after a one-millisecond gathering window, with at most 64 more queued; a full queue fails immediately. It seals membership before beginning remote validation. Later arrivals wait for another barrier, including when the previous CAS succeeded but its response is delayed. Every successful group therefore linearizes within every member’s invocation/response interval. Cancellation of one member cannot invalidate the others; failed barriers return errors to the whole group. The worker retains no observation for later requests and exits when its senders and queued work disappear. This batching reduces duplicate barriers without a clock-based read lease or a pod-local correctness dependency. Metadata contention still limits bucket performance.

Manifest collection lists candidates, then conditionally fences the directory root before deleting unreferenced manifests. The proof structure is the same as page collection, at the directory layer. S3 additionally retires obsolete physical versions of its control-register object using a list-before-barrier sequence. B2 manages bucket-metadata history internally.

Providers must implement atomic conditional publication and durable immutable uploads. The startup probe attempts a genuinely different stale update. Real B2 accepts an identical-metadata no-op with a stale revision; it rejects a conflicting replacement. Every protocol publication has fresh identities/fences, and no-op replay cannot introduce a different state.

General-purpose S3 is supported; unordered directory/Express listing semantics are not. S3 credentials need version-listing and version-deletion permissions even when the bucket is unversioned. Both versioned and unversioned MinIO buckets passed the same protocol tests. Real AWS qualification remains separate. See B2 evidence and setup.

Object lock and external retention rules can prevent reclamation. No external lifecycle rule or unrelated writer may delete live database files or alter the directory.

Local mode#

A lifetime OS lock admits one process per directory. The native owner recovers its checkpoint and selected journal suffix before readiness, then serves through the same HTTP backend used in native cloud fixtures. Writes use a temporary file, file fsync, atomic rename, and directory fsync. Every blocking mutation retains the lifetime lock even if its async waiter is cancelled. Crash-left temporary files are removed under that lock on reopen. Checkpoints and fenced collection run automatically. Local mode is not supported on shared/network filesystems, across multiple servers, or with cloned live process memory. See local format upgrades.

Provider retry boundaries#

The S3 control-register client and native B2 conditional publication path preserve unknown outcomes. In particular, an update that commits before its acknowledgement is replaced by an HTTP error must not be automatically retried and then reported as a definite comparison failure. S3 control PUTs and immutable uploads therefore have SDK retries disabled. Both provider bindings share an HTTP connector that also disables redirects and lower-layer retries: a 303 must not turn a PUT into a GET whose success is mistaken for a successful write. Read-only observations retain bounded SDK retries. Native B2 HTTP requests also disable automatic redirects and retries, with explicit read/authentication recovery handled above that boundary.

The shared publication layer resolves uncertain work through immutable proposal identity and durable receipts. Wire tests inject committed updates followed by 503 and redirects, and drop a connection after receiving a complete immutable payload. They verify one PUT attempt, preserved uncertainty, and the separately invoked stale-comparison result. Every new immutable-upload invocation needs a new admission charge, even when retrying the same application request.
