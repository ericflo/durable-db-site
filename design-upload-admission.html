Durable immutable-upload admission

Implemented in current source for fresh cloud namespaces; production qualification remains open. New budgeted namespaces use format 5, combining a cumulative immutable-upload byte/attempt ceiling with upload-free data collection. The earlier format-4 prototype remains readable with its existing ledger and collector behavior. Native library connections also use this allocator, with separate fresh-namespace initialization described below. Logical quotas and per-pod rate limits alone do not bound orphan uploads across scaling, cancellation, and delayed requests. Native serving additionally bounds journal admission per database; shared maintenance attribution and other provider costs remain additional work. It is not a storage-bill guarantee.

Charge before sending

The shared publication authority can allocate bounded, nonrefundable upload credits with its existing exact comparison. Allocation burns the entire grant durably before a process can use any of it. A process consumes credits before invoking an immutable PUT. Charge for the maximum number of underlying upload attempts, including bounded SDK retries; a logical API call is not necessarily one provider request. Both payload bytes and upload-attempt counts need separate ceilings, including zero-byte objects. Immutable pages, manifests, directory nodes, and proposals must all pass through this boundary, including a helper publishing another replica’s proposal.

Unused credits are lost when their process disappears. They are never restored from a cache, transferred to a replacement, or refunded because a lease expired, a pod died, or a listing did not find an object. A charged request can still reach the provider after those observations. A lost allocation acknowledgement may strand credits; uncertain recovery must never manufacture another usable grant. This conservative waste is visible operationally and traded for a hard upper bound on admitted immutable payload/attempt volume.

Deleting an object does not refund cumulative credits. Otherwise a delayed duplicate version or repeated create/delete workload could exceed the admitted volume. Operators explicitly increase the cumulative ceilings using revision-checked, idempotent administrative intent. A refill is not an automatic clock reset. The control plane must distinguish funded capacity, allocated credit, actual observed use, and logical live bytes; they are different quantities.

The intended authority record is a fixed-size global budget, independent of database count. Per-process grant state is disposable: losing it can only lose usable credit. It must not be checkpointed and replayed as fresh permission. The global allocator is common to B2 and S3, and must not require S3-only conditional immutable writes. The S3 control update’s retry boundary has been corrected before attempting this design.

Scope and format requirements

This ceiling covers immutable object payloads and upload attempts. It does not by itself cover authority-register traffic, reads/listings/deletes, request headers, TCP retransmission, provider accounting overhead, download bandwidth, or every component of the provider bill. Admission itself requires control requests; an exhausted-budget caller must not be promised that it can make unlimited free attempts. Gateway-level distributed request/egress/admin budgets and per-tenant isolation remain required. One tenant must not be allowed to consume a shared cluster ceiling merely because its logical data quota is small.

Enforcement needs a new publication format that older readers/writers refuse, including an incompatible authority-root envelope; a startup-only format check is insufficient for a previously running process. The first enforceable deployment should use a fresh dedicated namespace/bucket with no older in-flight uploads. Enabling a new counter over an old namespace cannot retroactively account for uploads that an old process sent before migration. A migration contract and export/restore tooling must precede any broader upgrade claim.

All immutable-upload paths pass through the allocator, including helper-generated directory nodes. Exhaustion after proposal submission remains an uncertain storage error, never a definite transaction abort. Reads and metadata collection continue without upload credit. Format 5 additionally collects data pages without immutable uploads, using the engine’s original observation and a global fence. Compaction remains funded and may defer; format-4 page GC also still needs funding. Deletion never restores credits. Sustained cleanup progress under adversarial workloads remains a qualification gate.

Initial model and remaining obligations

UploadCredits.tla models cumulative capacity in abstract positive upload units, two processes with crashes/restarts, additional grants whose acknowledgements can be lost, charging for bounded attempts, and arrivals after all originating processes disappear. Existing confirmed rights survive a failed attempt to obtain more. Explicit replenishment raises the ceiling without resetting allocation. The strengthened invariant requires charged units plus all usable local rights to fit inside durable allocation; delivered units fit inside the charge, and allocation fits inside the ceiling. Byte and attempt dimensions use the same componentwise checks.

Five negative controls refund a dead process’s grant, restore spent credit, allow arrival before charging, or reset allocation during a refill or initialization. The model deliberately has no expiration-based refund or clock authority. It is a finite abstraction, not a proof of HTTP request counting, provider billing, the Rust allocator, or composition with publication/collection. Administrative receipt eviction has implementation tests; a composed proof, per-tenant fairness, migration, and complete cleanup under exhaustion remain open.

Format and operation

Legacy format 3 remains unbudgeted. A fresh namespace opts into format 5 with both --upload-budget-bytes and --upload-budget-attempts (or matching DURABLE_DB_UPLOAD_BUDGET_* environment variables). Zero starts with uploads disabled; integers must be at most 2^53−1. The format/root envelope makes older binaries refuse access. Existing format-3 namespaces reject in-place activation, and existing format-4 namespaces retain their earlier collector. Once initialized, enforcement and ceilings come from metadata; omitting flags or supplying different startup limits cannot disable or reset them. Use the administrator API for later increases.

Both provider bindings use the same packed control document for budgeted formats. The format marker and incompatible root envelope remain visible, while budget counters, read fences, and collection cursors occupy one additional metadata entry. This accommodates B2’s ten-entry metadata bound without putting database entries back into bucket metadata. Admission reserves room for future cursors, maximum receipt storage, and an older binary’s startup probes. Old probes cannot override the ledger. Size and entry bounds are checked before mutation.

A bounded metadata record holds cumulative ceilings, allocated units, and a separate administrative configuration revision with eight intent receipts. Grants reserve up to 8 MiB and 32 attempts, clamped to available capacity, with enough bytes for the requesting object. A process spends both dimensions before invoking PUT. It replenishes only deficient dimensions and keeps previously confirmed rights in the other dimension. A lost additional-grant response cannot add usable rights, but does not erase older confirmed rights. Process loss, cancellation, and unknown acknowledgements can still strand credit; no balance is restored from disk. Allocation preserves the exact directory root and collector fields from its CAS observation; a concurrent change forces another comparison.

GET /v1/storage/upload-budget returns authoritative ceilings and allocation for administrators (null for local/unbudgeted storage). POST raises absolute ceilings with a request ID and expected configuration revision. Retry the same request after uncertainty. A retained matching receipt returns replayed: true with current status; changing its body is rejected. Once a receipt is evicted, its old expected revision conflicts rather than applying the increase again. Limits cannot decrease, and neither counter resets. Process metrics distinguish confirmed grants, charged upload attempts/bytes, and exhausted admissions; they do not replace the authoritative ledger or provider billing.

The upload transport now disables SDK retries and uses a shared HTTP connector that disables redirects and lower-layer retries explicitly. The SDK still supplies signing, workload credentials, endpoints, and encryption headers. A wire regression caught a 303 changing a PUT into a successful GET; the corrected connector refuses that transition. Tests cover all common redirects, transient statuses, zero-byte payloads, and a connection lost after receiving the complete body. Each invocation of the shared immutable upload boundary has at most one provider PUT attempt; application retries invoke the boundary again and must be charged again. Reads retain their separate bounded SDK retries. This property must remain a dependency-upgrade regression gate.

Native serving

Connection::with_upload_budget(limits) initializes a fresh native namespace before its first immutable registration. Reopen retains the durable ceilings and cumulative allocation regardless of supplied startup values. The incompatible owned-candidate-8 marker and required enforcement mode prevent an unbudgeted connection or older controller from claiming it. Existing unbudgeted namespaces cannot enable this in place. A zero ceiling refuses all PUTs while status and administrative replenishment remain available through the connection’s object interface.

The same allocator charges registrations (including abandoned candidates), journals, catalogs, tables and checkpoints. Its conditional allocation may invalidate a pending control comparison; a claim then conflicts and the caller creates a fresh incarnation using the same connection. Connection-local credit is never reconstructed from durable counters after replacement. The native HTTP backend exposes the existing administrator-only status/refill endpoints. Reads, including bounded table ranges, need no upload credit or additional control call. It does not reclaim journal/checkpoint data, qualify ownership timing or switch the CLI.

Native journal admission can wait for funding without leaving an unrecoverable gap. Only an admission failure before invoking the object provider returns the original owned upload handle. The worker retains its identity and memory reservation and retries the earliest such position at most once per second, outside the owner lock. A lost grant reply can strand credit but cannot send data. An attempted PUT, ambiguous provider response, or cancellation never returns a retry handle; those still require exact GET resolution or takeover. Funding resumes the waiting first PUT. Pending frames remain bounded by the existing journal and request limits.

The namespace ceiling intentionally stops shared writes when exhausted. Native serving also charges each database’s journal admission before reserving a shared journal position. An exhausted database receives 413 limit_exceeded; a neighboring funded database can continue, including in the same batch. Pending, committed and identical same-batch retries reuse admission. A later validation failure or cancellation can strand credit; it never refunds it.

The stable database name is the budget identity, matching the token scope. Credential rotation, owner replacement and checkpoint rebasing cannot reset it. One immutable ledger per name lives in the existing B+tree; one additional root reference occupies bucket metadata, with space reserved under B2’s ten-field/8 KiB subset. There is no per-bucket database-count cap from budgeting. Grant caching is bounded by the configured resident-database limit; eviction discards unused local rights without refunding the durable allocation. Checkpoints retain cached grants.

Protected creation installs defaults of 64 MiB journal bytes and 16,384 transaction admissions only if no ledger exists. Administrators can preprovision another allowance before creation using POST /v1/databases/{db}/upload-budget, and inspect it with GET. These endpoints use the same status, expected configuration revision, monotonically increasing absolute ceilings and eight-receipt retry protocol as the namespace endpoint. Missing names report zero counters and revision zero. Creation preserves an existing ceiling and spent allocation. Budgets do not automatically replenish; use the administrative control plane to fund them. The existing CLI backend does not implement these database endpoints.

Each new transaction charges one admission and its encoded journal contribution plus a complete frame header. This conservatively covers its contribution even when transactions share a frame. These are journal admission ceilings, not per-tenant physical storage or billing limits. Ledger/directory metadata, administrative lifecycle records, bootstrap, checkpoints and shared maintenance still use the namespace allowance. Reads/control/egress require separate protection. Complete attribution and fairness remain production gates.

TenantAdmission.tla composes two instances of UploadCredits with scoped journal assignment: 576 states at the minimal bounds, with negative controls for late charging and cross-scope credit. Atomic directory replacement and name binding are abstraction assumptions; Rust races, mixed-batch/retry tests and B2/S3 HTTP fixtures check that composition. No claim of full multitenant isolation or Rust refinement follows from this finite check.

Automatic native ledger cleanup

The native HTTP worker sweeps obsolete ledger records and directory pages every 60 seconds, outside serving locks. The same task invokes the existing provider maintenance operation even before tenant creation. For versioned S3 it removes historical control-register versions after a fresh comparison, preserving the current version and every mutable null version; B2 bucket metadata has no corresponding object history. Control writes remain outside the immutable-upload allowance. Each pass lists at most 128 candidates of each type, then conditionally fences the exact observed directory before testing reachability. The shared directory collector deletes physical versions of unreachable objects. It never removes the current entry for a database, even if that database has no remaining credit. Cumulative allocation is not refunded.

Cursors occupy one bounded metadata field and survive node replacement. Losing a fence reply permits no deletes; cancellation midway may defer candidates until the next sweep cycle. Only one sweep runs per worker, with a 30-second timeout; concurrent workers use the same comparisons. The sweep uses no immutable PUT and can run with exhausted upload credit. Ledger publishers rebuild immutable paths after any failed comparison, so a delayed publisher cannot resurrect a collected object. The existing reachability model and unbounded abstract proof cover this rule; implementation and provider tests are separate evidence.

This collector deliberately excludes journals, tables, registrations, recovery catalogs and checkpoints. Their reader/backup retention and reclamation protocol remains a production gate. Sweep frequency is an initial bound, not a demonstrated cleanup-throughput SLO.
