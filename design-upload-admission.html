Design notes

Durable immutable-upload admission

Implemented in current source for fresh cloud namespaces; production qualification remains open. New budgeted namespaces use format 5, combining a cumulative immutable-upload byte/attempt ceiling with upload-free data collection. The earlier format-4 prototype remains readable with its existing ledger and collector behavior. Native library connections also use this allocator, with separate fresh-namespace initialization described below. Logical quotas and per-pod rate limits alone do not bound orphan uploads across scaling, cancellation, and delayed requests. Native serving additionally bounds write admission per database; shared maintenance attribution and other provider costs remain additional work. It is not a storage-bill guarantee.

Charge before sending#

The shared publication authority can allocate bounded, nonrefundable upload credits with its existing exact comparison. Allocation burns the entire grant durably before a process can use any of it. A process consumes credits before invoking an immutable PUT. Charge for the maximum number of underlying upload attempts, including bounded SDK retries; a logical API call is not necessarily one provider request. Both payload bytes and upload-attempt counts need separate ceilings, including zero-byte objects. Immutable pages, manifests, directory nodes, and proposals must all pass through this boundary, including a helper publishing another replica’s proposal.

Unused credits are lost when their process disappears. They are never restored from a cache, transferred to a replacement, or refunded because a lease expired, a pod died, or a listing did not find an object. A charged request can still reach the provider after those observations. A lost allocation acknowledgement may strand credits; uncertain recovery must never manufacture another usable grant. This conservative waste is visible operationally and traded for a hard upper bound on admitted immutable payload/attempt volume.

Deleting an object does not refund cumulative credits. Otherwise a delayed duplicate version or repeated create/delete workload could exceed the admitted volume. Operators explicitly increase the cumulative ceilings using revision-checked, idempotent administrative intent. A refill is not an automatic clock reset. The control plane must distinguish funded capacity, allocated credit, actual observed use, and logical live bytes; they are different quantities.

The intended authority record is a fixed-size global budget, independent of database count. Per-process grant state is disposable: losing it can only lose usable credit. It must not be checkpointed and replayed as fresh permission. The global allocator is common to B2 and S3, and must not require S3-only conditional immutable writes. The S3 control update’s retry boundary has been corrected before attempting this design.

Scope and format requirements#

This ceiling covers immutable object payloads and upload attempts. It does not by itself cover authority-register traffic, reads/listings/deletes, request headers, TCP retransmission, provider accounting overhead, download bandwidth, or every component of the provider bill. Admission itself requires control requests; an exhausted-budget caller must not be promised that it can make unlimited free attempts. Gateway-level distributed request/egress/admin budgets and per-tenant isolation remain required. One tenant must not be allowed to consume a shared cluster ceiling merely because its logical data quota is small.

Enforcement needs a new publication format that older readers/writers refuse, including an incompatible authority-root envelope; a startup-only format check is insufficient for a previously running process. The first enforceable deployment should use a fresh dedicated namespace/bucket with no older in-flight uploads. Enabling a new counter over an old namespace cannot retroactively account for uploads that an old process sent before migration. A migration contract and export/restore tooling must precede any broader upgrade claim.

All immutable-upload paths pass through the allocator, including helper-generated directory nodes. Exhaustion after proposal submission remains an uncertain storage error, never a definite transaction abort. Reads and metadata collection continue without upload credit. Format 5 additionally collects data pages without immutable uploads, using the engine’s original observation and a global fence. Compaction remains funded and may defer; format-4 page GC also still needs funding. Deletion never restores credits. Sustained cleanup progress under adversarial workloads remains a qualification gate.

Initial model and remaining obligations#

UploadCredits.tla models cumulative capacity in abstract positive upload units, two processes with crashes/restarts, additional grants whose acknowledgements can be lost, charging for bounded attempts, and arrivals after all originating processes disappear. Existing confirmed rights survive a failed attempt to obtain more. Explicit replenishment raises the ceiling without resetting allocation. The strengthened invariant requires charged units plus all usable local rights to fit inside durable allocation; delivered units fit inside the charge, and allocation fits inside the ceiling. Byte and attempt dimensions use the same componentwise checks.

Five negative controls refund a dead process’s grant, restore spent credit, allow arrival before charging, or reset allocation during a refill or initialization. The model deliberately has no expiration-based refund or clock authority. It is a finite abstraction, not a proof of HTTP request counting, provider billing, the Rust allocator, or composition with publication/collection. Administrative receipt eviction has implementation tests; a composed proof, per-tenant fairness, migration, and complete cleanup under exhaustion remain open.

Format and operation#

Legacy format 3 remains unbudgeted. A fresh namespace opts into format 5 with both --upload-budget-bytes and --upload-budget-attempts (or matching DURABLE_DB_UPLOAD_BUDGET_* environment variables). Zero starts with uploads disabled; integers must be at most 2^53−1. The format/root envelope makes older binaries refuse access. Existing format-3 namespaces reject in-place activation, and existing format-4 namespaces retain their earlier collector. Once initialized, enforcement and ceilings come from metadata; omitting flags or supplying different startup limits cannot disable or reset them. Use the administrator API for later increases.

Both provider bindings use the same packed control document for budgeted formats. The format marker and incompatible root envelope remain visible, while budget counters, read fences, and collection cursors occupy one additional metadata entry. This accommodates B2’s ten-entry metadata bound without putting database entries back into bucket metadata. Admission reserves room for future cursors, maximum receipt storage, and an older binary’s startup probes. Old probes cannot override the ledger. Size and entry bounds are checked before mutation.

A bounded metadata record holds cumulative ceilings, allocated units, and a separate administrative configuration revision with eight intent receipts. Grants reserve up to 8 MiB and 32 attempts, clamped to available capacity, with enough bytes for the requesting object. A process spends both dimensions before invoking PUT. It replenishes only deficient dimensions and keeps previously confirmed rights in the other dimension. A lost additional-grant response cannot add usable rights, but does not erase older confirmed rights. Process loss, cancellation, and unknown acknowledgements can still strand credit; no balance is restored from disk. Allocation preserves the exact directory root and collector fields from its CAS observation; a concurrent change forces another comparison.

GET /v1/storage/upload-budget returns authoritative ceilings and allocation for administrators (null for local/unbudgeted storage). POST raises absolute ceilings with a request ID and expected configuration revision. Retry the same request after uncertainty. A retained matching receipt returns replayed: true with current status; changing its body is rejected. Once a receipt is evicted, its old expected revision conflicts rather than applying the increase again. Limits cannot decrease, and neither counter resets. Process metrics distinguish confirmed grants, charged upload attempts/bytes, and exhausted admissions; they do not replace the authoritative ledger or provider billing.

The upload transport now disables SDK retries and uses a shared HTTP connector that disables redirects and lower-layer retries explicitly. The SDK still supplies signing, workload credentials, endpoints, and encryption headers. A wire regression caught a 303 changing a PUT into a successful GET; the corrected connector refuses that transition. Tests cover all common redirects, transient statuses, zero-byte payloads, and a connection lost after receiving the complete body. Each invocation of the shared immutable upload boundary has at most one provider PUT attempt; application retries invoke the boundary again and must be charged again. Reads retain their separate bounded SDK retries. This property must remain a dependency-upgrade regression gate.

Native serving#

v0.19.0 uses budgeted format owned-candidate-23 for creation admission and clock-independent ownership. v0.18.1 uses format 21 and exempts catalog admission. Local format 15 and the cloud CLI format are unchanged.

Connection::with_upload_budget(limits) initializes a fresh native namespace before its first immutable registration. Reopen retains the durable ceilings and cumulative allocation regardless of supplied startup values. The incompatible owned-candidate-23 marker and required enforcement mode prevent an unbudgeted connection or older controller from claiming it. Existing unbudgeted namespaces cannot enable this in place. A zero ceiling refuses all PUTs while status and administrative replenishment remain available through the connection’s object interface.

The same allocator charges registrations (including abandoned candidates), journals, catalogs, tables and checkpoints. Its conditional allocation may invalidate a pending control comparison; a claim then conflicts and the caller creates a fresh incarnation using the same connection. Connection-local credit is never reconstructed from durable counters after replacement. The native HTTP backend exposes the existing administrator-only status/refill endpoints. Reads, including bounded table ranges, need no upload credit or additional control call. It does not qualify ownership timing or switch the CLI; journal reclamation is described below.

Native journal admission can wait for funding without leaving an unrecoverable gap. Only an admission failure before invoking the object provider returns the original owned upload handle. The worker retains its identity and memory reservation and retries the earliest such position at most once per second, outside the owner lock. A lost grant reply can strand credit but cannot send data. An attempted PUT, ambiguous provider response, or cancellation never returns a retry handle; those still require exact GET resolution or takeover. Funding resumes the waiting first PUT. Pending frames remain bounded by the existing journal and request limits.

The namespace ceiling intentionally stops shared writes when exhausted. Native serving also charges each database’s write admission before reserving a shared journal position. An exhausted database receives 413 limit_exceeded; a neighboring funded database can continue, including in the same batch. Pending, committed and identical same-batch retries reuse admission. A later validation failure or cancellation can strand credit; it never refunds it.

The stable database name is the budget identity, matching the token scope. Credential rotation, owner replacement and checkpoint rebasing cannot reset it. One immutable ledger per name lives in the existing B+tree; one additional root reference occupies bucket metadata, with space reserved under B2’s ten-field/8 KiB subset. There is no per-bucket database-count cap from budgeting. Grant caching is bounded by the configured resident-database limit; eviction discards unused local rights without refunding the durable allocation. Checkpoints retain cached grants, but retry funding can forfeit admission rights whose backing reserve has been consumed.

Protected creation installs defaults of 64 MiB combined admission/reserve bytes and 16,384 data/creation admissions only if no ledger exists. Administrators can preprovision another allowance before creation using POST /v1/databases/{db}/upload-budget, and inspect it with GET. These endpoints use the same status, expected configuration revision, monotonically increasing absolute ceilings and eight-receipt retry protocol as the namespace endpoint. Missing names report zero counters and revision zero. Creation preserves an existing ceiling and spent allocation. Budgets do not automatically replenish; use the administrative control plane to fund them. Native cloud CLI serving implements these database endpoints; unbudgeted local mode does not.

Each new data transaction or protected creation spends one volatile admission unit before assigning journal order. Creation uses the target database name as its payer while pricing the internal catalog record and its affected table/manifest paths. Pending and committed retries reuse admission. Refusal leaves the catalog unchanged and takes no journal position; funded neighbors can continue. Credential rotation and revocation remain operator-funded from the namespace allowance: exhausting a tenant’s data budget must not prevent an administrator revoking its credentials. A separate administrative allowance and attribution of policy work remain open. Its byte contribution covers the journal record and complete frame header, new checkpoint rows, and affected table/manifest paths. A tenant byte grant of G now allocates 2*G from its ceiling: G for these admission rights and a separate durable maintenance reserve of G. The namespace physical allocator is unchanged. This is conservative funding, not provider billing. Losing local admission rights does not erase the unissued reserve, and observing the reserve never recreates those rights.

Manifest growth uses G(k) = 2 * (164 + k + 8 * (68 + k)): two singleton paths through the maximum nine levels. A leaf entry includes a 152-byte table reference; internal entries include a 56-byte blob reference. Both include the boundary length/key and a ten-byte node header. The second path covers split propagation and root growth. Existing descriptors on affected paths are charged separately. At the 2,048-byte key bound, Gmax = 38,280 bytes.

The data writer flushes at 4 MiB or 4,096 rows. A size-triggered flush closes more than 4,194,304 - 67,598 = 4,126,706 encoded bytes; a row-triggered flush closes 4,096 rows. Thus F(b, r) = ceil(b * Gmax / 4,126,706) + ceil(r * Gmax / 4,096) funds the manifest growth for these flushes. Rounding each contribution upward preserves the bound when inputs share a table. Each remaining boundary flush ends on a new row or an affected base table; neither terminal input can end two such runs.

  • Each new metadata, receipt, value or tombstone row with key length k and value length v contributes its singleton data/index size 106 + 3*k + v, plus G(k) and F(14 + k + v, 1).
  • Each affected base table with authenticated data size D contributes 5*D + Gmax + F(D, floor(D/33)). The fivefold term covers any data/index reblocking; every checkpoint row occupies at least 33 encoded bytes. The growth terms cover retained rows becoming new table boundaries, including neighbors’ rows. Deleted rows and expired receipts still count.
  • Existing leaf and ancestor bytes count once per transaction, using nine temporary references to deduplicate sorted paths. An append past the base also contributes Gmax for splitting the old rightmost path. Manifest seeks use the bounded cache; pricing reads no table indexes or values, and missing evidence fails closed.

The name-scoped allocator deducts the sum in one operation. Pending, committed and identical same-batch retries reuse that charge. Distinct writes can pay for the same dirty table repeatedly. This uses no persistent paid-table set or refunds. Format owned-candidate-23 refuses older accounting policies and requires a fresh native namespace; local format remains owned-candidate-15.

These bounds deliberately overestimate work. The adversarial reblocking fixture uploads 533,873 bytes including its manifest against a 2,819,918-byte allowance. Value-heavy tables pay a fractional manifest charge rather than a full maximum-size path for every retained row. Tightening the allowance remains useful work. Creation now prepays its journal and conservative checkpoint contribution against the target tenant. Bootstrap, policy changes, ledger publications and construction-time claims for the shared catalog remain namespace-funded. Reads/control/egress need separate protection.

Unchanged checkpoint tables reuse authenticated manifest intervals without reading indexes. Rewrites finish each base manifest group before entering the next and split overflowing groups evenly, so an insertion or deletion does not regroup untouched siblings. Fresh bulk builds still pack full nodes. This reduces shared upload amplification; admission includes existing paths and new manifest encoding, and construction attempts use the durable funding described below. The full manifest is still traversed during checkpointing; admission seeks only affected intervals. Merely warming receipt metadata for a retry/refusal does not dirty a database. When the journal has not advanced and no publication is pending, maintenance discards that clean cache without an immutable PUT or authority mutation.

Durable construction funding#

Before building a checkpoint, the owner recomputes a conservative allowance from the exact live or recovered projection. Only changed databases contribute; old receipts are covered by base copies, and only new receipts add rows. Charges include existing table reblocking and manifest paths. Construction-time claims still exclude the complete internal catalog identity; attributing that shared retry/recovery work is unfinished. A user database named durable-catalog with another generation pays normally. Initial creation prepayment does not yet close this construction-attribution gap.

One conditional directory replacement claims all participating tenants’ allowances together, checking the owner/recovery origin and collection generation. Every tenant is preflighted before any ledger upload; refusal cannot debit a funded neighbor. Ordinary renewal and namespace grants can change the authority nonce during a large batch. Funding reuses staged ledgers only while the tenant-directory root and metadata collection fence remain unchanged; a conflicting ledger or sweep requires rebuilding. Bounded 64-entry directory batches publish through one final root, so the tree batching limit is not a tenant-count limit. If reserve is insufficient, the claim may allocate the shortfall from the tenant’s still-unallocated byte ceiling. That recovery-only funding grants no new admission rights and consumes no transaction-admission unit.

A confirmed claim authorizes one bounded construction attempt. The upload wrapper deducts bytes before each PUT, including failed or cancelled PUTs, and refuses overruns before invoking the provider. Every physical PUT also consumes namespace credit. A lost funding reply strands its entire claim; cancellation, process replacement and collection never refund it. Replacement owners can claim unissued reserve, but cannot reconstruct admission grants or reuse spent attempt rights. Resolving an already staged publication reuses its objects without another construction claim.

Retry funding can consume reserve backing unused local admission rights. Those rights are reduced before the potentially applied CAS, so later writes cannot spend the same backing. Tenant status exposes maintenance: {funded_bytes, allocated: {bytes, attempts}}. These nested attempts count checkpoint construction claims, including uncertain claims, rather than individual provider PUTs. The outer byte allocation includes both admission grants and all reserve funding; its attempt counter counts grants for data and creation admissions.

Admission prepays a conservative construction allowance. Finite credit cannot fund unlimited failures or recovery work. Once both reserve and remaining ceiling are exhausted, construction refuses until an administrator increases the ceiling. Because the current checkpoint is shared, this can pause shared recovery or maintenance; it is not a fault-independent tenant availability guarantee. Keep namespace physical credit funded separately. Funding metadata, administrative work, request/egress costs and stronger progress isolation remain open.

Attempt starts back off for 1, 2, 4, 8, 16, then at most 30 seconds. Cancellation and incoming requests cannot bypass the gate. Staged publication resolution does not rebuild or wait; confirmed publication resets pacing. Restart discards pacing but never restores spent credit.

TenantAdmission.tla now directly checks this reserve protocol with two names, a takeover and three possible attempts. Its invariant covers same-name funding, combined admission/reserve allocation, nonrefundable claims and owner fencing. Six negative controls exercise unfunded use, cross-scope debit, missing prepayment, recreated admission, refunded attempts and stale ownership. UploadCredits separately guards physical grants and late arrivals. Atomic directory replacement and name binding remain assumptions; byte sizing, Rust refinement, complete attribution and liveness remain separate obligations. See verification.

Automatic native metadata cleanup#

The native HTTP worker sweeps obsolete ledger records, recovery catalog entries and shared directory pages every 60 seconds, outside serving locks. The same task invokes the existing provider maintenance operation even before tenant creation. For versioned S3 it removes historical control-register versions after a fresh comparison, preserving the current version and every mutable null version; B2 bucket metadata has no corresponding object history. Control writes remain outside the immutable-upload allowance. Each pass lists at most 128 candidates of each type, including journal frames, then conditionally fences the exact observed authority before testing reachability against both its budget directory and recovery catalog. A candidate is protected if either directory references it; a missing or corrupt catalog fails closed. The shared directory collector deletes physical versions of unreachable objects. It never removes the current entry for a database, even if that database has no remaining credit. Cumulative allocation is not refunded.

Cursors occupy one bounded metadata field and survive node replacement. Losing a fence reply permits no deletes; cancellation midway may defer candidates until the next sweep cycle. Only one sweep runs per worker, with a 30-second timeout; concurrent workers use the same comparisons. The sweep uses no immutable PUT and can run with exhausted upload credit. Each budgeted sweep advances a separate metadata fence, including sweeps with no obsolete tables and unchanged cursors. Funding can reuse staging across ordinary control changes only while that fence and its tenant-directory root match. Initialization, refill, admission grants and maintenance claims now share that ledger publication path. A definite conflict caused only by renewal, read barriers or namespace grants reuses the original metadata. A changed tenant-directory root or metadata fence requires rebuilding, malformed formats fail closed, and uncertain replies grant no retry permission. Eight unsuccessful comparisons with unchanged scope stop without uploading another copy. Catalog publishers still rebuild after a failed comparison. A delayed publisher cannot resurrect a collected object. The existing reachability model and unbounded abstract proof cover this rule; implementation and provider tests are separate evidence.

Native format owned-candidate-23 requires a fresh namespace and rejects earlier experimental formats. There is no in-place migration for older budgeted native namespaces. Local storage remains owned-candidate-15; unbudgeted remote storage uses owned-candidate-23-unbudgeted; this accounting change does not invalidate v0.9.0 local directories. The same sweep deletes frames at or before the published checkpoint cut in its named journal, plus journals from earlier registered ownership epochs. It validates the inline checkpoint descriptor before fencing; an unpublished checkpoint, uncertain fence or malformed descriptor grants no deletion permission. The later suffix, newer epochs, different incarnations at the cut’s epoch and other journal partitions are retained. Registrations bind incarnation, epoch, namespace and encoding; one cached registration avoids a provider read per frame. Late arrivals in a closed earlier epoch can be reclaimed on a later sweep. Inline checkpoint descriptors remove header-object uploads and orphans. The sweep also lists up to 128 table objects and protects current and explicitly retained checkpoint references through the bounded manifest walker. A persisted collection generation invalidates staging before any table deletion; unchanged generations permit reuse across ordinary control updates. The sweep makes no immutable PUT and never refunds credits. Raw snapshots are not pins. Registrations, catalog headers, scheduled backups and large-manifest cleanup progress remain production gates. The native operator API provides one explicit backup slot; see retention. Sweep frequency is an initial bound, not a demonstrated cleanup-throughput SLO.
