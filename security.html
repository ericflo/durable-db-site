Security and resource isolation

Trust boundaries

Database users can be buggy or hostile. They can send arbitrary requests, race transactions, abandon responses, and exhaust their allowed quotas. They cannot access object-store credentials, the signing key, server files, or another tenant’s token. Compromised servers and malicious storage providers are outside the current threat model.

Only administrators create databases, set initial quotas, mint scoped tokens, change access policies, or request explicit maintenance. Signed HMAC-SHA256 capability tokens bind one database, read/write permission, and expiration. Enabled database policies additionally bind a fresh incarnation, credential generation, and token ID. A separate expiring metrics-only capability authorizes only GET /metrics; it uses a distinct HMAC domain and never carries the signing key. Signature checks use constant-time verification. Database authorization uses the same validated manifest as data access, including every retry after a missing page and every receipt replay. Key names are data, never filesystem paths. Database identifiers are validated independently.

Tokens are bearer capabilities. Keep admin credentials on the server, use HTTPS at ingress, issue short-lived application tokens, and avoid embedding long-lived credentials in static assets. CORS is denied by default; a trusted application gateway supplies browser origin and user authorization policy. Token expiry uses wall-clock time; synchronize node clocks. The storage safety protocol does not use clocks.

Resource controls

Logical bytes and key quotas live in the same manifest CAS as the write. Competing pods cannot separately approve growth beyond the quota. Oversized values, operations, manifests, results, and page rewrites are rejected. Global concurrent requests, rate-limiter entries, and immutable caches are bounded. No request loads the entire database.

Cache budgets account for encoded data plus conservative entry/key overhead. They are not a hard process-RSS promise: decoding, HTTP buffers, TLS, allocator overhead, and concurrent requests consume additional memory. Kubernetes memory limits and sensible concurrency settings provide the outer bound. OOM or SIGKILL may interrupt availability but cannot acknowledge an uncommitted manifest.

Rate limits are per database per pod, not a strict global billing limit. More pods increase the aggregate allowance. Successful logical quotas do not cap the temporary physical cost of aborted uploads. Fresh cloud namespaces can enable cumulative upload admission, which durably burns shared byte/attempt grants before immutable PUTs. Crashes, retries, deletion, and delayed arrivals do not refund those grants. The namespace ceiling is shared: it does not prevent one tenant from consuming another tenant’s allocation, and excludes control traffic, reads, egress, and other provider charges. Format 5 collects unreachable data pages without upload credit; compaction still needs funding. Per-tenant physical admission, gateway request/egress/admin budgets, billing alerts, and sustained cleanup under adversarial load remain release gates. Do not sell logical quotas or the global upload ceiling as a hard storage-bill cap.

Current request budgets default to 20 units/second and a burst of 40; a commit costs five units and other authenticated requests cost one. All database tokens share their database budget; administrator tokens share one budget across databases. Deployment settings make this policy explicit and configurable within finite bounds. Accounting samples time inside the admission lock, retains fractional credit exactly, and never evicts a depleted budget just because it has been idle for 60 seconds.

Each database also has a per-pod concurrency allowance of max(1, concurrency / 4): two requests with the default eight global slots. All tokens for that database share the allowance, which remains held while reading the request body. Cancellation and timeout release it. Administrator and metrics requests have separate fixed-principal allowances, including when a database is named _admin or _metrics. Tenant churn cannot evict those principals from admission: the map has at most 4,096 tenant slots plus two fixed control entries. This limits one database’s ability to monopolize a pod; it does not reserve capacity against several cooperating databases, protect pre-request connections, or create a cluster-wide quota. With global concurrency set to one, a single request necessarily occupies the only slot.

Manifest validation checks object namespaces, ordered/nonoverlapping page bounds, quotas and accounting, and receipt structure before serving data or performing maintenance. Data pages must match their declared length, key range, key/byte counts, checksum, and canonical encoding. Both cache layers check the expected digest. These checks reject malformed state; they cannot detect every coherent modification by someone with storage credentials and are not a substitute for backup or access control.

Operations

Use a private dedicated bucket and least-privilege permissions to one prefix. Enforce TLS, encryption at rest, and conditional writes with bucket policy where supported. Do not configure external object/version expiration for the database prefix: the cluster performs physical version reclamation after its own reachability checks and fences, and an external lifecycle rule can delete live state. Never expose object credentials to database clients. The server emits control/error categories, not request keys, values, credentials, or provider error strings.

Create new databases through the protected PUT operation, which atomically enables revocable credentials and records a permanent provisioning receipt. For existing legacy databases, enable the durable access policy after upgrading every server, before distributing application credentials. Legacy databases intentionally keep legacy behavior until that explicit migration. A protected database supports individual revocation (128 IDs per generation) and generation advancement, both persisted with the data manifest and enforced after all pods/caches disappear. Policy changes fence older prepared writes without changing user data revisions. Format 2 makes pre-policy engines fail closed; activation is not compatible with rolling back to those binaries. In-flight reads may finish from their earlier authorized snapshot.

Current source builds issue expiring, domain-separated administrator capabilities with token --admin; their payload contains only expiration. The legacy ddb_admin_ credential contains the signing key and remains accepted with a legacy hex key file, or an explicitly compatible JSON keyring. New keyrings disable it by default. Disabling that envelope does not revoke a leaked signing key: rotate the key itself. Never delegate an administrator credential to monitoring or tenant applications.

Overlapping key rotation uses one active signing key and at most three additional verification keys. Expansion, issuer promotion, and retirement require distinct completed rollouts; key files are loaded once on startup. Wait for old issuers to stop and their capabilities to expire before graceful retirement. A still-serving partitioned process remains part of the completion barrier. Per-database credential generations are independent of this key rotation. Audit-event export, tenant lifecycle deletion, full deployment qualification, and independent security review remain release gates.

Logical archives contain plaintext keys and values. Export files and validation spools use private filesystem permissions; archives require independently protected storage and retention. Checksums detect corruption, not replacement by an attacker who can recompute them. Restore validates a private copy before remote mutation, refuses unrelated existing databases, and creates a fresh policy incarnation without restoring tokens. Keep the partial destination isolated until full verification succeeds; see recovery.
