Understand

Security and resource isolation

Trust boundaries#

Database users can be buggy or hostile. They can send arbitrary requests, race transactions, abandon responses, and exhaust their allowed quotas. They cannot access object-store credentials, the signing key, server files, or another tenant’s token. Compromised servers and malicious storage providers are outside the current threat model.

Only administrators create databases, set initial quotas, mint scoped tokens, change access policies, or refill upload allowances. Signed HMAC-SHA256 capability tokens bind one database, read/write permission, and expiration. Protected database policies additionally bind a fresh incarnation, credential generation, and token ID. A separate expiring metrics-only capability authorizes only GET /metrics; it uses a distinct HMAC domain and never carries the signing key. Signature checks use constant-time verification. Database authorization uses the same committed view as data access and receipt replay; remote responses also validate a fresh owner permit after sealing their result. Key names are data, never filesystem paths. Database identifiers are validated independently.

Tokens are bearer capabilities. Keep admin credentials on the server, use HTTPS at ingress, issue short-lived application tokens, and avoid embedding long-lived credentials in static assets. CORS is denied by default; a trusted application gateway supplies browser origin and user authorization policy. Token expiry uses wall-clock time; synchronize node clocks. The storage safety protocol does not use clocks.

Resource controls#

Admission checks logical bytes and key quotas against both durable state and accepted pending writes before reserving journal order. Ownership fencing prevents competing pods from independently acknowledging growth beyond that quota. Oversized values, operations, manifests, results, and page rewrites are rejected. Global concurrent requests, rate-limiter entries, and immutable caches are bounded. No request loads the entire database.

Cache budgets account for encoded data plus conservative entry/key overhead. They are not a hard process-RSS promise: decoding, HTTP buffers, TLS, allocator overhead, and concurrent requests consume additional memory. Kubernetes memory limits and sensible concurrency settings provide the outer bound. OOM or SIGKILL may interrupt availability; an acknowledgement requires a durable journal prefix and valid serving permission.

Rate limits are per database per pod, not a strict global billing limit. More pods increase the aggregate allowance. Successful logical quotas do not cap the temporary physical cost of aborted uploads. Fresh cloud namespaces can enable cumulative upload admission, which durably burns shared byte/attempt grants before immutable PUTs. Crashes, retries, deletion, and delayed arrivals do not refund those grants. The namespace ceiling is shared: it does not prevent one tenant from consuming another tenant’s allocation, and excludes control traffic, reads, egress, and other provider charges. Format 5 collects unreachable data pages without upload credit; compaction still needs funding. Per-tenant physical admission, gateway request/egress/admin budgets, billing alerts, and sustained cleanup under adversarial load remain release gates. Do not sell logical quotas or the global upload ceiling as a hard storage-bill cap.

Current request budgets default to 20 units/second and a burst of 40; a commit costs five units and other authenticated requests cost one. All database tokens share their database budget; administrator tokens share one budget across databases. Deployment settings make this policy explicit and configurable within finite bounds. Accounting samples time inside the admission lock, retains fractional credit exactly, and never evicts a depleted budget just because it has been idle for 60 seconds.

Each database has a per-pod concurrency allowance of max(1, concurrency / 4): two requests with the default eight tenant slots. All tokens for that database share the allowance, which remains held while reading the request body. Cancellation and timeout release it. Administrator budget, access-policy, token and metrics operations share two additional control slots with metrics-only capabilities, so several tenants filling the data pool cannot exclude recovery and monitoring. Existing per-principal concurrency and rate limits still apply to those control requests. The total admitted HTTP bound is concurrency + 2; trusted control traffic can itself fill its two slots. Administrator data traffic retains the tenant pool and a separate principal allowance. Validated capabilities and matched operational routes select the reserve; tenant paths/names such as _admin or _metrics cannot obtain control capacity. Tenant churn cannot evict control principals from admission: the map has at most 4,096 tenant entries plus three fixed operator entries. These limits do not protect pre-request connections or create a cluster-wide quota.

Journal, catalog, checkpoint and table decoders check their object namespaces, bounds, ordering, accounting and receipt structure before exposing recovered state or collecting referenced objects. Immutable blocks must match their expected length, checksum and canonical encoding. Both cache layers check the expected digest. These checks reject malformed state; they cannot detect every coherent modification by someone with storage credentials and are not a substitute for backup or access control.

Operations#

Use a private dedicated bucket and least-privilege permissions to one prefix. Enforce TLS, encryption at rest, and conditional writes with bucket policy where supported. Do not configure external object/version expiration for the database prefix: the cluster performs physical version reclamation after its own reachability checks and fences, and an external lifecycle rule can delete live state. Never expose object credentials to database clients. The server emits control/error categories, not request keys, values, credentials, or provider error strings.

Create databases through the protected PUT operation, which enables revocable credentials and records a permanent provisioning receipt. Individual revocations (128 IDs per generation) and credential generations are journaled with catalog changes, survive checkpoint recovery and remain enforced after all pods and caches disappear. Pending revocation blocks new affected write admission; committed revocation also fences receipt replies. Policy changes leave data revisions unchanged. In-flight reads may finish from their earlier authorized snapshot. Older storage formats require export and restore.

The CLI issues expiring, domain-separated administrator capabilities with token --admin; their payload contains only expiration. The legacy ddb_admin_ credential contains the signing key and remains accepted with a legacy hex key file, or an explicitly compatible JSON keyring. New keyrings disable it by default. Disabling that envelope does not revoke a leaked signing key: rotate the key itself. Never delegate an administrator credential to monitoring or tenant applications.

Overlapping key rotation uses one active signing key and at most three additional verification keys. Expansion, issuer promotion, and retirement require distinct completed rollouts; key files are loaded once on startup. Wait for old issuers to stop and their capabilities to expire before graceful retirement. A still-serving partitioned process remains part of the completion barrier. Per-database credential generations are independent of this key rotation. Audit-event export, tenant lifecycle deletion, full deployment qualification, and independent security review remain release gates.

Logical archives contain plaintext keys and values. Export files and validation spools use private filesystem permissions; archives require independently protected storage and retention. Checksums detect corruption, not replacement by an attacker who can recompute them. Restore validates a private copy before remote mutation, refuses unrelated existing databases, and creates a fresh policy incarnation without restoring tokens. Keep the partial destination isolated until full verification succeeds; see recovery.
