Transactional key-value storage that lives in your bucket.

durable-db is one Rust binary that serves atomic transactions and ordered scans over HTTP. S3 or Backblaze B2 holds the authoritative data. API servers keep only disposable state, so you can add, replace or stop all of them without moving the database. On a laptop, a local directory replaces the bucket.

TypeScript

import { Database } from '@durable-db/client';

const db = new Database({ url, database: 'my-app', token });

// One atomic read-modify-write. A conflict reruns the
// callback; a lost response retries the identical commit.
await db.transaction(async (tx) => {
  const task = await tx.get<Task>(`tasks/${id}`);
  if (!task || task.done) return;
  const done = (await tx.get<number>('stats/done')) ?? 0;
  tx.set(`tasks/${id}`, { ...task, done: true });
  tx.set('stats/done', done + 1);
});

// Ordered scans, a page at a time.
const { items, cursor } = await db.list<Task>({
  prefix: 'tasks/', limit: 20,
});

Status

Where it stands today

Local and cloud serving use the native engine. The cloud CLI discovers peers through DNS, places fixed partitions by stable member identity, and uses clock-independent permits with bounded forwarding and resident state.

Use one dedicated bucket per deployment, private peer networking and TLS at application ingress. Fund upload allowances, set process/replica limits and keep independently protected backups. v1.0.6 recovered 385/385 acknowledged writes in its scale-down run, with a 41.31s largest readback gap. Its separate 32-worker, 1 KiB B2 load baseline completed all operations at 9.34 writes/s and 141.38 reads/s. Write tails reached 53.18s; a larger-value run hit cumulative funding limits. Write performance and conservative maintenance precharging need improvement. These are short fixtures, not SLOs. See the measured results, operating scope and deferrals, and recovery procedure.

Supported in 1.0

  • Transactions, ordered scans, scoped credentials, quotas and bounded admission

How it works

The bucket is the database.
Servers are replaceable.

Every server uses the same bucket and prefix. DNS membership places native partition owners; object-store permits authorize serving. No attached volume or separate coordinator is required.

  1. Immutable journals, owned partitions

    Each partition orders transactions and uploads immutable journal frames. Ownership and checkpoints publish through conditional writes. Responses validate a fresh writer permit; competing commits from one database revision cannot both succeed.

  2. Caches can be lost

    Servers keep bounded memory and disk caches and rebuild everything else from object storage. Cached bytes are verified by SHA-256. Losing a cache costs time, never data.

  3. Uncertain writes have an answer

    If a commit’s response is lost, send the identical request again. A stored receipt returns the original result, and the old revision check stops a second application.

  4. No clocks or leases in cleanup

    Garbage collection lists candidates, fences the state with a conditional write, and only then deletes. Pod-local locks, clocks, caches and Kubernetes leases never decide what is safe to delete.

On a laptop, the same API runs over a local directory held by an exclusive OS lock. See the architecture for the full protocol.

Quick start

Run it on your laptop in a minute

No bucket, container or extra service needed. v1.0.6 ships a static binary for Linux x86_64; other platforms can build from source.

  1. Install

    The installer verifies the release checksum and installs one file in ~/.local/bin. While the repository is private, authenticate the gh CLI with an account that has access.

    curl -fsSL https://ericflo.github.io/durable-db-site/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"

  2. Start a server

    It listens on 127.0.0.1:7654. The first start creates data/admin.key, which signs administrator tokens. Keep it private.

    durable-db serve --data ./data

  3. Create a database and commit

    In another terminal. Values are base64, so d29ybGQ= is world. A read returns the revision to send with your next commit.

    export DDB_TOKEN=$(durable-db token --key-file ./data/admin.key --admin)
curl -X PUT http://127.0.0.1:7654/v1/databases/demo \
  -H "Authorization: Bearer $DDB_TOKEN" -H 'Content-Type: application/json' \
  -d '{"request_id":"create-demo","limits":{"max_bytes":67108864,"max_keys":100000}}'
curl http://127.0.0.1:7654/v1/databases/demo/commit \
  -H "Authorization: Bearer $DDB_TOKEN" -H 'Content-Type: application/json' \
  -d '{"expected_revision":0,"request_id":"first-write","writes":[{"key":"hello","value":"d29ybGQ="}]}'
curl http://127.0.0.1:7654/v1/databases/demo/read \
  -H "Authorization: Bearer $DDB_TOKEN" -H 'Content-Type: application/json' \
  -d '{"keys":["hello"]}'

The contract

What you can rely on

The contract the first production release must qualify. Transactions are scoped to one database; use one database per tenant or application.

  • Serializable transactions within a database. Every commit names the revision it read. If anything committed since, it gets 409 and the client recomputes.
  • Durable acknowledgements. An acknowledged write must survive the loss of every API server and every cache.
  • Ordered reads. Keys sort by UTF-8 bytes. Scans take a prefix, a range, a cursor and a direction, and every key and scan in a request reads one snapshot.
  • Exact retries. Receipts for the last 128 commits return the original result to an identical retry.
  • Limits that refuse instead of truncating. Quotas, request sizes, caches and per-principal request budgets reject work before anything is published.
  • Out of scope. Transactions that span databases, and long-running historical snapshots.
