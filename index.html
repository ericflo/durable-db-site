A transactional key-value database stored in a bucket.

durable-db is one static Rust binary that serves atomic transactions and ordered scans of JSON values over HTTP. The data is immutable objects in Backblaze B2 or another S3-compatible bucket, so servers keep no state: add them, remove them or kill every one, and nothing is lost.

  • One binary, about 8 MB

  • No conditional writes, leases or synchronized clocks
  • Modelled in TLA+
  • Apache-2.0

TypeScript SDK

import { Database } from '@durable-db/client';

const db = new Database({ url, database: 'demo', token });

await db.set('users/ada', { name: 'Ada' });
const ada = await db.get<{ name: string }>('users/ada');

// Atomic. If another transaction changes a key this one
// read, nothing is written and the callback runs again.
await db.transaction(async (tx) => {
  const from = (await tx.get<number>('accounts/a')) ?? 0;
  const to = (await tx.get<number>('accounts/b')) ?? 0;
  if (from < 30) throw new Error('insufficient funds');
  tx.set('accounts/a', from - 30);
  tx.set('accounts/b', to + 30);
});

// An ordered scan of a prefix, one page at a time.
const page = await db.list({ prefix: 'accounts/', limit: 20 });

HTTP with curl

export URL=http://127.0.0.1:7654/v1/databases/demo
export AUTH="Authorization: Bearer $(durable-db create demo)"

# Two keys written by one transaction.
curl $URL/commit -H "$AUTH" -d '{"writes": [
  {"key": "accounts/a", "value": {"balance": 100}},
  {"key": "accounts/b", "value": {"balance": 100}}]}'
# {"revision":1}

# Move 30, only if accounts/a is still at version 1.
# Sent again with the same key, it is applied once.
curl $URL/commit -H "$AUTH" -d '{
  "checks": [{"key": "accounts/a", "version": 1}],
  "writes": [
    {"key": "accounts/a", "value": {"balance": 70}},
    {"key": "accounts/b", "value": {"balance": 130}}],
  "idempotency_key": "transfer-7f3a"}'
# {"revision":2}

# An ordered scan of a prefix, read at one revision.
curl $URL/read -H "$AUTH" \
  -d '{"scans": [{"prefix": "accounts/"}]}'

How it works

One writer per database, decided by a claim object in the bucket

Storage needs only PUT, GET, HEAD, LIST and DELETE with read-after-write consistency. There are no conditional writes, no leases, no synchronized clocks and no consensus service. Backblaze B2 and S3 run the same algorithm.

  1. Every object is immutable

    A database is frames, tables, manifests and a claim. A server writes them under an epoch name with a fresh random part, so two servers never write the same key. That is why no write needs to be conditional.

  2. One server writes a database, and holds a claim

    To take a database, a server lists the claims, picks a higher epoch and PUTs its own claim object. If it then lists a claim higher than its own, it deletes its own and stops.

  3. A successor deletes the old claim before it reads

    It deletes every lower claim first. Only then does it read the newest manifest and the frames that follow it. Nothing the previous owner acknowledges after that point can be missed.

  4. Every acknowledgement waits for a HEAD on the claim

    A commit is one PUT of a frame, then one HEAD. If the claim still exists, the frame was stored before any successor began to read, so the successor has it. If the claim is gone, the server acknowledges nothing and the client retries with its idempotency key.

  5. Strong reads and cleanup use the same check

    A strong read waits for a HEAD that began after the read arrived. The owner deletes superseded objects only after a HEAD that began after its newest manifest was stored. A server that has been replaced fails the check. It acknowledges nothing and deletes nothing.

On one machine the same binary runs the same protocol over a local directory. The architecture page has every step, a table of what happens when things fail, and the reasoning for each rule.

Performance

Measured on Backblaze B2 and on a local directory

A commit costs one upload and one HEAD, so storage latency is the floor. One database has one writer. Its throughput comes from grouping: every transaction that arrives while an upload is in flight joins the next frame.

What you get

Transactions, scans and per-database limits over HTTP

One deployment serves many databases. Give each tenant or application its own database and its own token.

  • Atomic transactions

    All writes of a transaction apply together or not at all. Checks on key versions and key ranges make it conditional. Writes are strictly serializable, and transaction scope is one database.

  • Ordered scans

    Keys are strings ordered by their bytes. Scan by prefix, start and end, in either direction, one page at a time. Every key and scan in one request is read at the same revision.

  • Two read consistency levels

    strong, the default, is linearizable and costs one storage round trip, shared by all reads waiting at that moment. session returns a consistent snapshot at the revision you have seen or newer, from memory.

  • Idempotent retries

    With an idempotency key, a repeated transaction returns the original result instead of applying twice. A 503 on a commit means the outcome is unknown, and repeating the request is always safe.

  • Tokens, quotas and rate limits

    A database token grants read or write on one database and is checked before anything touches storage. Each database has its own byte quota and request rate. One request revokes all of its tokens.

  • Autoscaling with no volumes

    A Kubernetes Deployment with no persistent volume, scaled by an ordinary HorizontalPodAutoscaler. A pod that is told to stop hands its databases over first. A pod that is killed loses nothing.

  • Automatic cleanup

    The owning server deletes the frames, manifests and tables its newest manifest no longer needs, including every old version on a versioned bucket. No lifecycle rule is needed.

  • The same binary everywhere

    One binary serves a laptop from a directory and a cluster from a bucket. It exposes Prometheus metrics for requests and storage calls, and a readiness probe that reports whether storage is reachable.

Verification

What was checked

The protocol is one TLA+ model of ownership, commit, checkpoint, collection and deletion. The Rust code is written to follow it step for step, and is tested with injected faults, real server processes and a real bucket.

3.59 milliondistinct states at 2 writers, 2 epochs and 2 transactions, and 4.11 million more with deletion and 1 transaction. TLC explores both exhaustively and finds no violation. 11 of 11negative controls refuted. Each turns off one protocol rule in the model and must produce a counterexample. 200 seedsof a randomized fault-injection test pass: three nodes, dropped, half-applied and late storage requests, crashes, stale owners and deletions. 20,933 transfersin a ledger verified exactly on a three-node kind cluster backed by B2, while the autoscaler scaled 2 → 5 → 2 and a pod was force-killed. Of 13 million reads sent alongside without retries, 102 failed.

Bounded model checking is evidence about a model. It is not a proof of the Rust implementation or of every deployment. The verification page lists the assumptions, what the model leaves out, the defects that these tests and a review found, and the obligations that remain.

Limits

Limits, stated plainly

Read these before you choose it.

By design

  • One writer per database at a time. Spread load by using more databases, not more servers per database.
  • A commit costs one upload and one HEAD. A strong read costs one HEAD, shared among concurrent reads. Session reads cost none.
  • Transactions do not span databases.
  • No historical reads. Only the current state is kept.
  • A deleted database's name cannot be reused.
  • Merging the oldest table rewrites the database, each time it grows by half. Memory does not grow with the database, but the uploads do. The default quota is 1 GiB per database; larger ones have not been measured.
  • Servers of a deployment trust each other. They talk plain HTTP inside the cluster, and all are trusted with the bucket. Per-tenant CPU accounting and billing are not provided.
Limits of this design →

Not done yet

  • Only Backblaze B2 has been exercised among cloud providers. Amazon S3 and other S3-compatible stores share the code path except for the upload call, but have not been run.
  • No soak of many hours on a real multi-node cluster. The Kubernetes test ran on kind. Memory was measured under load for minutes on a local directory, not for hours and not on a bucket.
  • Many databases committing at once were slow on B2 in the last measurement: with 64 of them, one commit in a hundred took over two seconds. The cause is not understood.
  • No point-in-time restore. Deletions are permanent. Protect the bucket with your provider's replication.
  • The prebuilt binary is Linux x86_64 only. Other platforms build from source.
  • The repository is private for now. The installer uses the gh CLI, signed in to an account with access.
  • No independent review yet. The model does not cover conditional transactions or liveness.

Quick start

Run it on one machine, then on a bucket

The first three steps need no bucket, container or other service.

  1. Install

    The script downloads the release for Linux x86_64, verifies its checksum and puts durable-db in ~/.local/bin. While the repository is private it uses the gh CLI, which must be signed in to an account with access.

    curl -fsSL https://ericflo.github.io/durable-db-site/install.sh | sh

  2. Start a server

    It listens on 127.0.0.1:7654 and stores everything in ./data. The first start creates ./data/admin.key, the signing key for tokens.

    durable-db serve --data ./data

  3. Create a database, write and read

    In a second terminal, from the same directory. durable-db create creates the database and prints a write token for it.

    export URL=http://127.0.0.1:7654/v1/databases/demo
export AUTH="Authorization: Bearer $(durable-db create demo)"

curl -X PUT $URL/keys/greeting -H "$AUTH" -d '"hello"'       # {"revision":1}
curl $URL/keys/greeting -H "$AUTH"                            # "hello"

  4. Serve from a bucket

    For Backblaze B2, create a private bucket and an application key restricted to it. Every server of a deployment needs the same signing key. At startup the server probes the bucket and refuses to start if storage does not behave as required.

    openssl rand -hex 32 > admin.key && chmod 600 admin.key

export AWS_ACCESS_KEY_ID=<keyID> AWS_SECRET_ACCESS_KEY=<applicationKey>
durable-db serve \
  --bucket my-bucket \
  --endpoint https://s3.us-west-002.backblazeb2.com \
  --key-file admin.key
