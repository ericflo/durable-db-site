Development

Use the pinned Rust toolchain in rust-toolchain.toml. All Rust builds use kache, including local tests. Source builds also need a C toolchain and CMake for AWS-LC; the installed static executable needs neither. Java 11+ runs TLC, and Node 24 runs the client, examples and documentation tools.

scripts/install-kache.sh
export PATH="$PWD/.tools/bin:$PATH"
export KACHE_CONFIG="$PWD/.kache.toml"

cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked --all-targets
cargo test --locked --release --test publication ten_thousand_databases_split_page_recover_and_collect -- --ignored --exact
scripts/check-model.sh
scripts/check-proof.sh

Native client contract checks explicitly provision 1 GiB per database with DURABLE_DB_TEST_ADMISSION_BYTES=1073741824; half funds admission and half prepays durable maintenance. The long document-tail and receipt-eviction cases exceed the default 64 MiB under conservative shared-table pricing; the fixture retains the previous 512 MiB admission allowance. The common JavaScript fixture uses the existing administrator budget endpoint. Runtime defaults and dedicated refusal tests are unchanged. Run this contract locally after admission-pricing changes, before waiting for the release build.

The backup recovery fixture uses a larger bounded request budget so its 16,641-key interrupted restore tests recovery rather than waiting for the default four-commit-per-second allowance. Admission tests retain default-policy coverage and use a controlled clock for exact refill and eviction checks.

The two Rust test commands run the complete required suite: the capacity regression is opt-in so ordinary cargo test does not run its large directory sweep in debug mode. CI runs it explicitly in release mode. The local command uses your host target. Woodpecker runs that same regression on musl, sharing the target used by the shipped static binary instead of building a separate optimized GNU target.

The model command checks every current-engine model and its required controls. The proof command above checks abstract publication safety; journal and research proofs have separate commands below. These checks do not establish that the Rust implementation refines the models. See verification for each theorem’s assumptions and scope.

Formal check inputs#

Each model’s .checks descriptor declares every positive configuration, unsafe variant and reachability control. An unsafe variant must violate its named invariant. A reachability control forbids a desired scenario and must produce a counterexample reaching it; this is coverage, not a liveness proof. The candidate wrapper copies the maintained dependencies into a temporary directory and removes it on exit. Logs remain under .tools/candidates/.

Each proof’s .proof descriptor declares:

tag|log-name
dependency|ImportedModule
negative|control-name|focused-theorem|expected-action|sed-mutation

Dependencies are optional; every proof requires a negative control. An empty theorem field checks the entire mutated proof. Every positive proof uses strict checking and fresh fingerprints. A mutation must change its source and fail its expected obligation; a parser or tool-launch error cannot pass. The runner requires all declared controls to execute and keeps checker input separate from descriptor input.

Focus a mutation on the first lemma affected by the changed protocol. Checking only a caller could accidentally assume the broken lemma. Large solver queries should be split into explicit proof steps so checks remain reliable on the CI builder; do not hide failures by weakening a property or reusing old fingerprints.

Adding a proof needs a descriptor and its own Docker stage. It should not require changing the common runner or invalidating unrelated proofs. CI may skip repeated dependency execution only when the stage inherits the exact checked dependency. Local commands check dependencies by default.

Real provider checks#

Cloud checks are opt-in and require a dedicated disposable bucket. Never run them against application data. Configure credentials privately through the provider environment; do not put them in commands, reports or logs.

export DURABLE_DB_DISPOSABLE=1
export DURABLE_DB_TEST_PROVIDER=b2 # or s3
export DURABLE_DB_TEST_BUCKET=durable-db-test-UNIQUE
export DURABLE_DB_TEST_CONTEXT='Client placement and provider region'
export DURABLE_DB_REGISTER_REPORT="$PWD/register-report.json"
export DURABLE_DB_JOURNAL_REPORT="$PWD/journal-report.json"

cargo test --locked --test provider_register -- --ignored --exact unchanged_metadata_still_requires_an_exact_comparison
cargo test --locked --test journal_cloud -- --ignored --exact journal_reconnect_unknown_responses_and_late_uploads

The register fixture permits at most thirteen conditional attempts, including a bounded reconnect barrier. The journal fixture permits seventeen PUT attempts of at most 33 KiB each. Provisioning, reads, verification and cleanup are additional operations. After success or failure, remove every physical version, the bucket and its temporary credentials. MinIO exercises the S3 binding; it does not qualify AWS. The older publication fixture has its own environment contract in tests/s3.rs.

For component work, Native::connect_storage and S3::connect_storage return the same providers::Connection. Its objects() and authority() expose transports without initializing publication metadata. into_published explicitly opens the current engine. Each conditional register replacement receives a fresh mutation identity, including replacements with otherwise identical metadata. Raw connections do not grant serving permission or provide tenant admission. objects().get_range(key, range, object_size) reads an exact immutable slice up to 8 MiB, checking the provider’s total size, returned range and body length. It fails rather than downloading a whole object when range semantics are unsupported. HTTP regressions check that immutable writes leave authority metadata untouched and that redirects or lost replies do not cause a second PUT.

Connection::root() creates a fresh clock-independent candidate. Every remote claim uploads one immutable registration and one write-once positive permit before its captured conditional publication. Activation revokes all unresolved predecessor permits, including the checkpoint owner, before recovery. select_prefix persists exact journal discoveries; Opening::recover constructs a private projection. The native HTTP worker seals responses, then validates its permit with a fresh uncached GET. No successful validation can be reused for later requests. Local open_local instead retains the lifetime directory lock, preserving format 15. Remote formats 23 and 23-unbudgeted refuse older timed writers. The cloud CLI now uses the membership-driven native controller. See controller scope.

For the opt-in large-object range check, use the same disposable provider credentials and set DURABLE_DB_RANGE_REPORT to a local output path:

cargo test --locked --test provider_ranges -- --ignored --exact bounded_ranges_of_a_large_immutable_object

It writes one 16 MiB object and verifies five bounded slices, missing/size errors and rejection above the 8 MiB cap. It does not retry an uncertain upload. Delete all versions and revoke the temporary key after either outcome. The live transaction checks exercise the current grouped-write and selected-recovery path.

For native tables and their overlapping snapshot merge, set DURABLE_DB_TABLE_REPORT and use the same disposable provider environment:

cargo test --locked --test native_tables -- --ignored --exact native_tables_use_bounded_blocks_and_recover_revisioned_ordered_rows

This uploads four immutable objects for 3,072 history rows and 1,025 newer rows, checks one-block point reads, bounded caching, merged ordered scans with deletion markers and cache-free reopening. It does not initialize a serving engine or publish a manifest. Remove all four objects’ physical versions and the dedicated bucket, and revoke its temporary key after either outcome. The native index uses the existing Rust toolchain and kache configuration.

For native cluster integration, api::Cluster::open takes a Partitions directory, ClusterConfig, one shared cache, an Arc<Auth> keyring and a Tokio watch receiver of peer socket addresses. Bind the listener before advertising its address. The caller supplies membership; the controller performs acquisition, recovery, placement and retry scheduling. Serve it through the ordinary App/router. Keep the layout fixed across restarts and membership changes. A peer list is a scheduling hint, never ownership authority. Reproduce the focused checks with cargo test --locked --lib cluster:: and cargo test --locked --lib layout_. The disposable-provider controller fixture is cargo test --locked --test checkpoint_cloud -- --ignored --exact native_http::membership_places_partitions_and_recovers_over_http; use the provider environment and cleanup rules below. It accepts supplied local membership snapshots and does not qualify Kubernetes discovery.

Kubernetes load measurements#

scripts/benchmark-kubernetes.py runs the SDK benchmark through the shared Service on three distinct hosts, using the maintained deployment manifests and an image pinned by digest. Supply a fresh dedicated bucket, its scoped provider environment as a private JSON file, a signing key and its administrator token:

python3 scripts/benchmark-kubernetes.py \
  --context YOUR_CONTEXT --image REGISTRY/durable-db@sha256:IMAGE_DIGEST \
  --storage-env-file /private/storage.json \
  --signing-key-file /private/admin.key --admin-token-file /private/admin.token \
  --output ./load-result --disposable \
  --concurrency 32 --value-bytes 65536

The default matrix uses 32 databases, 1/4/16/32 workers and 20 operations per worker, with separate closed-loop write/read phases. Override --databases, --workers and --operations for a focused regression. Each database gets a 64 MiB cumulative upload allowance; the namespace gets 1 GiB. A failed worker stops, remaining unstarted operations stay visible, and final verification checks the last value/revision and upload counters. Resource reports retain kubelet RSS, working set, CPU counters and restart counts; ten-second sampling can miss peaks. Setup is excluded from phase throughput, but retries and backoff are included. These runs do not establish sustained-load or latency SLOs.

For a focused long-journal cold-recovery check, add --cold-recovery --databases 1 --workers 1 --operations 100 --value-bytes 65536. The workload retains expected values and exact acknowledged requests in its own process. The controller freezes every database process using the existing same-UID pause helper, removes all pods, confirms zero remain, and starts three new pod identities without disk caches. Freezing first prevents graceful shutdown from checkpointing away the suffix. A nonce-bound file barrier then releases point/scan checks, exact receipt retries and a new write/readback. Reports retain separate warm/cold resource epochs and server logs. Confirm the cold selection logs actually discover the intended long suffix; a successful read from a recent checkpoint alone does not qualify this case. The optional fault sidecars are confined to this disposable fixture. Run node scripts/test-benchmark.mjs for fast controls that reject corrupt cold values and incorrect retry receipts.

The runner removes its namespace and retains workload results and bounded server logs even on failure. The caller must remove all bucket versions, delete the dedicated bucket and revoke its scoped key afterward. Never reuse a result directory or omit failed runs from a comparison. The native load evidence records the release baseline and its failures.

CI and publication#

The release verification record links source commits, Woodpecker builds, artifact hashes, standalone checks and actual public-installer downloads.

The website’s release badge comes from the installer’s default tag in scripts/install.sh. Its recent milestones are the newest five ## sections of docs/verification-results.md. Releases therefore need no homepage edit; change site/home.html only when the product status or contract changes. The README names the release once, in its opening notice; record per-release details in the verification results rather than the README or homepage. Published pages and their navigation groups are listed in site/build.mjs.

Woodpecker is the only CI system. GitHub Actions are disabled. Changes go directly to main while the repository is private. Successful main builds push the public documentation with a repository-scoped SSH deploy key, then wait up to ten minutes for the public deployment.json marker to match CI_COMMIT_SHA. A successful push alone does not qualify publication: GitHub can fail the later Pages deployment while leaving the previous site live. On failure, inspect the public site’s deployment status and retry the same checked artifact; do not claim the site is current until its marker and evidence match. A newer source push cancels the previous running pipeline in this setup; finish local iteration before pushing and let the required run complete so verification and publication can finish.

The publisher updates only files that still match its prior generated hashes, preserves independent site edits/deletions and unrelated files, and records preserved paths in deployment.json. It pulls/rebases before every push and rebuilds against the newest site after a push race; it never force-pushes. Obsolete generated files are removed only when still unedited. The first manifest is bootstrapped from the last publisher commit. Site authors may edit the public repo concurrently; preserved overrides need deliberate reconciliation with generator changes.

If GitHub reports success while the public marker and files remain stale, first compare the site branch with the intended artifact. A Pages rebuild of that existing branch (gh api --method POST repos/ericflo/durable-db-site/pages/builds) can refresh hosting without another content commit. Still require the public marker and installer to match before declaring delivery.

Within that delivery window, an explicitly failed public deployment permits one empty-commit retry of the identical site tree. The script checks that the remote branch has not moved, uses a normal non-forced push, and never retries merely because the API is unavailable, rate-limited or still pending. Public status inspection needs no API token. Repeated failure still fails CI. node --test scripts/test-publish-docs.mjs checks matching/stale markers, HTTP errors, invalid source identities, recovery, unknown status, a competing publisher and the retry bound using isolated transport/clock doubles.

The Docker build requires Rust formatting, lints and tests; the full client/Pi suite; every active model and its controls; and the publication and journal proofs. It builds the static Linux executable, runtime image and documentation artifacts. The 10,005-database regression retains every assertion and runs in release mode on x86_64-unknown-linux-musl; the rest of the Rust suite runs in debug mode. Before publishing artifacts, scripts/check-release.mjs checks the archive checksum, contents and source version, then runs its binary with an empty PATH: protected creation, exact retries, ordered reads, backup/restore and recovery after a forced stop. It removes its temporary server, data and credentials and writes checks/release.json into the artifact image. Rerun it against a downloaded archive with node scripts/check-release.mjs PATH/TO/durable-db-linux-amd64.tar.gz (optional second argument: an older version to check).

Rust, JavaScript, autoscaling evidence checks, individual models and individual proofs have separate cache stages. Harness edits do not rerun unchanged Rust or client checks. Client/example README files are excluded from the Docker context because neither tests nor the site generator consume them; guide edits do not invalidate client verification. Changing client code reuses the same source-built executable without repeating unchanged Rust work. A shared lock serializes formal-check heaps on the builder. Compiler stages stop their kache daemon on exit while preserving the compilation cache.

The build step forwards TERM/INT to its buildctl child and waits for remote cancellation before exiting. This lets the client cancel remote work explicitly before the shell exits. A disposable BuildKit job canceled in 5.8 seconds; success and failure exit codes were also preserved. The qualification record retains the preceding canceled-build delay and probe setup failures.

Client contracts use the completed debug executable and finish before optimized compilation starts, avoiding CPU contention with the release build and capacity regression. The synthetic 10,005-entry check advances Tokio’s timer waits while retaining both budget formats, all entries and assertions. It checks capacity and correctness, not physical latency. Real network/failure tests retain their own deadlines. A local release-mode sample takes 31.01s instead of 87.57s; compilation is excluded and CI timing remains platform-dependent.

The pipeline archives its exact commit with canonical file permissions. Uncommitted files and checkout metadata are excluded, and the temporary context is removed on exit. File metadata matters to Docker cache reuse as well as content. Docker cache invalidation, Git archive.

Dependency audits#

scripts/audit-dependencies.sh
npm --prefix clients/javascript audit
npm --prefix examples/web-app audit
npm --prefix site audit

The Rust audit verifies the pinned cargo-audit binary, fetches current advisories, rejects vulnerabilities and warnings without exemptions, and records the advisory database commit. CI runs dependency audits outside Docker’s layer cache, so new advisories can block an unchanged lockfile. A failed advisory fetch fails the gate. Audit success does not rule out undiscovered vulnerabilities.

The disposable server started by scripts/test-client.sh uses explicit bounded request budgets of 1,000,000 units/second and burst units. This keeps receipt-eviction and Pi conformance tests from sleeping on production admission defaults. The dedicated Rust and HTTP admission tests still exercise those defaults, refill, shared principals and exhaustion. This fixture setting is not a production recommendation or a database throughput result.

For checkpoint composition, use the same disposable provider environment, set DURABLE_DB_CHECKPOINT_REPORT, and run:

cargo test --locked --test checkpoint_cloud -- --ignored --exact native_checkpoints_recover_selected_suffix_across_complete_reopen

This initializes the current native candidate format, writes 1,024 database generations, checkpoints the first 16 selected frames, removes those covered fixture frames, and reconstructs through a fresh provider connection and controller. It checks nine suffix frames, retained receipts, excluded late old-owner data and zero control calls during reconstruction. Before suffix recovery it also checks lazy checkpoint point reads, ordered scans and receipt resolution, including 1,000 warmed iterations with zero provider calls and all 1,024 databases at their checkpoint revision. It rewrites the combined image and reopens it with every resident limit set to one, checking all 1,024 database generations without resident rows or receipts. Its timing samples use a debug build; they are not serving SLOs. It stops writers before takeover; it does not qualify live HTTP serving, automatic collection or AWS. Delete all physical versions and the dedicated bucket and revoke temporary credentials after either outcome. Checkpoint construction itself performs no cleanup.

The native provider qualification requires a fresh dedicated disposable bucket named durable-db-test-*, DURABLE_DB_DISPOSABLE=1, DURABLE_DB_TEST_PROVIDER=b2 or s3, DURABLE_DB_TEST_BUCKET, the provider’s credentials, and DURABLE_DB_NATIVE_HTTP_REPORT for JSON evidence. It exercises the real native HTTP path and waits for two normal 60-second cleanup sweeps, including one after takeover publishes a recovery catalog and a new checkpoint. Covered frames in both the earlier and current journals must disappear before the second reopen. Two complete connection/cache reopens then verify values, receipts and spent credit. Recovery must claim retained tenant reserve without allocating new admission rights, and a later cold reopen must preserve those counters. The caller must remove every physical version, the bucket, and any temporary workload key afterward. It keeps the first server alive across clock-independent takeover and requires subsequent reads and receipt retries to fail. Each warmed read validates one fresh permit GET with no authority calls. It does not qualify Kubernetes placement, AWS or a sustained SLO, or establish a production operating envelope.

The native cloud CLI fixture is cargo test --locked --test cluster_cli -- --ignored --nocapture, with the same disposable-provider/report environment above. It kills all compute, starts with stranded namespace credit, refills through the ready administrator endpoint before owner recovery, then verifies values/receipts, incompatible layout refusal and another cold recovery. The regular test in that file checks invalid CLI settings before provider access. DNS unit checks use cargo test --locked --lib api::membership; the residency model uses scripts/check-model.sh OwnerResidency.
