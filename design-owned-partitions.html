Design notes

Owned partitions and durable log batches

Status: native local and cloud serving are integrated. The 1.0 scope covers one trust domain on B2 or a local directory; the larger design goals below remain the long-term direction. Local mode uses exclusive filesystem ownership. Cloud mode uses clock-independent permits, fixed database mapping, DNS membership, owner forwarding and bounded resident state. Existing-host qualification uses ordinary Kubernetes hosts; no restricted compute profile is required.

Why the serving engine changed#

Replaceable compute does not require every request to reconstruct authority independently. Treating those as equivalent was an architectural overconstraint. A running node can retain useful state when ownership, handoff, recovery and resource bounds make that state safely replaceable.

The previous shared serving path used Authority::read_fresh to conditionally update the bucket authority even for a cache-hit read. Grouping amortized that operation without removing it; writes and collectors contended on the same revision. The directory removed the former database-count cap without creating independent write capacity. Its 100,005-entry correctness test is not evidence of 100,005 concurrently useful databases.

The B2 combiner measurement completed four-writer phases at 1.051 operations/second with second-scale latency. The later one-hour baseline also remains far below the intended operating envelope. Safety checks cannot establish performance suitability. The native engine must meet both requirements.

The current serving protocol uses native owners in both local and cloud CLI modes. Ordinary cloud data responses validate a per-writer permit GET instead of updating the shared authority. Raw control observations are also read-only hints; claims and activation still need exact comparisons. Provider bindings, API behavior, authorization and adversarial fixtures remain shared. Passing behavioral checks does not close the performance and recovery gates.

Exclusive local serving#

A local directory has one process-lifetime OS lock. The native local adapter retains that guard through its serving worker and every pending filesystem mutation; cancellation cannot hand off the directory while an old write is still running. A paused process retains ownership. A new process acquires the lock only after the old process and its pending work have relinquished it, then selects and recovers the old journal before serving. This supplies local exclusion without remote permit reads; it does not extend to shared/network filesystems.

The private adapter passes the retained directory guard directly to the shared root controller. It exposes only the HTTP backend, never a reusable clock or cluster connection. PID changes refuse use. There is no physical clock dependency or renewal timer. Remote native owners instead use revocable permits without local filesystem or bounded-clock assumptions. LocalExclusive.tla checks exclusive guard retention, recovery-before-serving and pending-I/O cancellation; filesystem locking/fsync semantics, process exit, journal correctness and implementation refinement remain separate assumptions/obligations.

This design does not weaken acknowledgement to mean RAM replication or a future upload. Optional asynchronous durability would be a different contract and is not part of this proposal.

Separate control from data#

A slow conditional control register is useful for creating a new ownership epoch, publishing a durable handoff decision and changing placement. It should not be on every application read or every independent database write.

A partition contains many databases and has one current writer incarnation. Its owner maintains the committed view and groups accepted transactions into a bounded log batch. Other processes route requests to that owner. The number of databases is not the number of buckets, partitions or permanently assigned processes. Placement and partition-count limits must be measured and documented; this does not reintroduce a fixed small database cap.

Independent partition control#

Connection::into_partitions opens a shared, budgeted B+tree directory. Each stable u32 partition ID selects its own native control record and object prefix. The existing owner, journal, checkpoint, tenant ledgers and collector run unchanged within that scope. A partition can contain many databases; this is not a database-count limit or a bucket per partition.

Control changes use the existing publication/rebase protocol. Ordinary native reads and acknowledgements validate the partition’s permit directly. Moving one partition does not revoke another. Shared collection protects directory pages and control records; partition collection cannot list or delete another partition’s data. Format 6 prevents legacy cloud servers from interpreting control records as database manifests.

The shared upload ceiling covers both control publication and partition data. Per-partition and per-tenant ceilings remain additional limits. Shared control publication needs upload credit, including partition collection fences; administrators can replenish the shared ceiling directly. Complete attribution of shared overhead and fair maintenance progress are deferred beyond the single-trust-domain 1.0 scope.

Root::advertise publishes an address with a fresh ownership incarnation. api::Forward discovers that route, caches it and forwards one bounded request. The destination checks the incarnation, tenant policy and ordinary serving permission; a stale address cannot select another owner. A failed request returns to the caller, whose explicit retry refreshes the route. Routing checks and limitations include live B2/MinIO takeover.

api::Cluster accepts membership snapshots and automatically reconciles placement. A fixed layout is installed before any partition entry; SHA-256 maps database names independently of membership. Rendezvous ranking of stable member IDs chooses a preferred node independently of its current socket address. Only the existing conditional claim, revocation and recovery protocol can make it serve. Removing a placement drops its local serving entry; already admitted requests retain their selected backend and still validate its permit. api::Membership supplies DNS snapshots to the cloud CLI; resident reservations follow retired owners and I/O. Deployment and performance qualification remain. See the partition verification scope.

Revocable writer permits#

A writer incarnation gets a unique positive permit object. Create it with one physical PUT, resolve that upload positively, and only then publish the incarnation through an exact conditional control update. Never recreate or retry that permit’s PUT. A restart uses a fresh identity. The existing transports already disable PUT retries and redirects; these rules also have to hold at the controller boundary.

For each bounded group of responses, prepare a consistent read result or complete the contiguous durable journal prefix, seal the group, then issue a fresh uncached GET of its permit. Only matching live bytes authorize that group. Missing objects, provider errors and corrupt bytes refuse service. A successful GET cannot admit a request that started later. This includes retry receipts and metadata reads, not just value reads.

Takeover first revokes every unresolved predecessor permit, then discovers and durably selects each predecessor’s journal prefix before serving. An old positive GET reply can arrive after takeover: its already-started reads may linearize before revocation, and its acknowledgements refer only to a prefix durable before that GET. Late uploads after revocation earn no new acknowledgement. Revocation must be permanent: physically removing the single positive version leaves absence meaning refusal, without permanent negative tombstones. Delete markers must never be collected in a way that exposes a live older version.

The small RevocableOwner model checks one handoff without clocks, including delayed replies and uploads. Seven deliberately broken variants expose why creation-before-publication, one physical PUT, fresh reads, sealed groups, contiguous durability and revoke-before-scan are necessary. Bounds and assumptions are explicit. This ordering now drives the native runtime. The model is not a proof of repeated placement, collection composition or Rust.

This removes bucket-wide conditional updates from the native ordinary data path, not all provider I/O: a read group costs a GET; a write group costs its durable upload plus a GET. Independent writers can validate independently. Batching amortizes calls but adds waiting. The first B2 experiment measures 32–67 ms median GET latency and about 200 validations/second at concurrency 16, with a one-second outlier in the sequential phase. These short raw-provider phases are not database performance qualification; zero-network cached reads are not promised by this mechanism.

The provider must never return old positive permit bytes to a GET started after confirmed revocation. Real tests cannot prove that consistency contract. The first B2/MinIO deletion experiment passes; provider consistency, lost replies, transport caching and AWS deployment still need explicit qualification. No hardware timing guarantee is substituted for this obligation.

Renewal without a provider call per partition#

The earlier timed-delegation route is retained as fallback evidence only. It would amortize provider renewal through shorter child grants, but relies on continuously advancing clocks with justified error bounds. The existing hosts do not provide that contract. Its models and proofs remain historical evidence for the removed timed controller; they do not authorize restricting the first production deployment to special hosts.

Delayed control updates#

A timeout does not cancel a provider operation. A freeze, activation or prefix selection may apply after the caller has stopped waiting or its permit has been revoked. Such late application does not authorize serving, issuing grants or acknowledging transactions.

Each request must capture an exact comparison, payload and invocation identity before sending. Only its matching current response can confirm a view. Raw metadata reads may be stale; an uncertain operation requires exact revalidation. A conflict describes that invocation alone and cannot prove that an earlier abandoned operation never applied.

A confirmed control update is historical evidence, not reusable permission. Activation revokes ancestors before opening recovery. Retrying an uncertain update requires a new exact comparison; it never recreates a permit or authorizes a later response. Placement must preserve the same immutable identity and revocation boundaries.

providers::Connection::control() implements the request lifecycle in Rust, including invocation matching, bounded metadata and explicit uncertainty. It uses the same nonce-stamped conditional register for B2 and S3. Its real HTTP tests keep provider processing alive after caller cancellation. It does not interpret root intervals or placement, and confirmed metadata records a historical successful comparison rather than continuing permission.

The request session, exact acquisition, durable ancestry and permit checks describe the current boundaries. They still need a complete composition with journal selection, placement and the serving engine. Earlier timed placement/request models remain historical fallback evidence.

Transaction concurrency#

Independent partitions address contention across databases. The current API also compares a whole-database expected_revision, so transactions on unrelated keys within one database can still conflict. Moving that API onto a faster journal does not remove this second bottleneck. The performance qualification must include both many active databases and disjoint-key writers in one database.

The replacement transaction layer should validate bounded key and range read sets against one consistent snapshot. Range checks must detect phantoms, including inserts and deletions; reading several keys must not mix snapshots. The existing whole-database revision condition retains its strict meaning for existing callers. More precise conditions require an explicit versioned API and client support. The internal validation component below has a preceding model; the HTTP API still uses its existing revision condition.

An owner can order accepted transactions within a batch and validate each against its accepted predecessors. Client-visible reads and acknowledgements must follow the contiguous durable prefix; speculative changes cannot escape through a read. Snapshot retention, expired snapshots, request receipts, quota checks and bounded conflict metadata belong in that protocol. A benchmark must report retries and fairness as well as aggregate throughput, so batching cannot hide starvation or repeated recomputation by individual clients.

Bounded transaction validation#

src/transactions/validation.rs now implements an internal conflict window for one database. It validates point keys, ordered ranges and the strict whole-database revision condition against every accepted predecessor, including transactions awaiting durability. Disjoint keys can share a snapshot. Range checks cover absent keys; insertions, deletions and no-op writes all record their mutated keys. The owner must capture the token and values from the same durable view, serialize evaluation/admission with acceptance, and advance that view only through the journal’s contiguous durable prefix.

Snapshot tokens belong to one validator incarnation. Recovery or movement creates a fresh instance and expires old tokens. Conflict metadata can be reclaimed only for committed revisions; a snapshot older than the retained history expires instead of passing an incomplete check. Pending writes cannot be discarded to make capacity. Errors leave the validator unchanged by that invocation; they do not resolve an earlier request. Receipt recovery must precede validation, and snapshot expiry cannot justify recomputing a transaction after an uncertain result. The existing whole-database condition still conflicts with every intervening transaction, even one whose only change is a receipt.

Defaults retain at most 4,096 transactions, 65,536 key references and 4 MiB of key bytes counted across those references. Repeated keys within a transaction are deduplicated; repeated keys across transactions remain charged. Each request has at most 128 read terms and 128 mutation keys, with 1,024 bytes per key. Range validation inspects at most 4,096 index entries across a transaction before returning a work-limit error. If its snapshot already matches the accepted revision, range validation needs no index scan. These bounds cover this component’s key storage and container cardinality, not whole-process RSS or tenant admission.

A preceding finite model and adversarial Rust tests cover read dependencies, phantoms, pending predecessors, history reclamation and disjoint transaction acceptance. This component does not store values or implement authenticated wire tokens, receipts, tenant quotas, journal reservation or ownership. It is not used by the HTTP engine yet. Verification and remaining composition obligations.

Immutable batches and acknowledgement#

Assign each batch a fresh identity from its partition, unique writer epoch and never-reused sequence position. Encode accepted transactions, request identities, resulting database revisions and the preceding log digest. The process sends at most one PUT for that identity. An unknown PUT outcome stalls that sequence; it may be resolved by reading and checking the exact object. It must not allocate a replacement transaction identity or send different bytes under the same name.

Uploads may be pipelined, but acknowledgement advances only through a contiguous durable prefix. A completed upload at position three cannot justify acknowledging it while position two is unresolved. Before acknowledgement, the writer must also verify its serving permission. Merely having started the upload while permission was valid is insufficient. If validation fails after a PUT might have landed, the response is uncertain, not a definite conflict or rollback: recovery may still retain that batch.

The HTTP worker coalesces adjacent queued commits through the live owner’s existing grouped-write API. One scheduler yield gathers concurrent callers; there is no minimum group size or batching timer. Groups hold at most 128 requests and fit a conservative wire/record estimate within the remaining journal byte allowance, capped at 4 MiB. Creation and policy changes delimit groups. Request-local group errors fall back to individual evaluation; uncertain storage/funding failures return unavailable without silently repeating preparation. Each reply retains its own identity, authorization and durable-prefix requirement. Several completed responses can share one fresh permit GET; ordinary transactions do not update shared authority. Admission funding and checkpoint/control work still require separate publications; the composed correctness and performance gates remain open.

Journal implementation boundary#

The bounded immutable journal lives in src/journal/. Its objects live under journal/, outside the existing page collector’s blocks/ namespace. A writer always receives a fresh random epoch and never reopens an old epoch for writing. Frames bind the partition, epoch, sequence, previous digest, length-delimited records and a SHA-256 digest. Decoding validates lengths before allocating record views.

A prepared upload is single-use. Lost or cancelled responses retain an unresolved position; resolution performs a point GET and compares the exact bytes, never a second PUT. A missing result remains uncertain because an upload can still arrive. Completed positions become consumable only in contiguous order. A count and byte budget bound frames held by the queue, uploads and consumers, including unresolved work. Record views borrow their frame, so a small retained record cannot silently pin an unaccounted whole-frame allocation. Each replay reader permits one live frame, reserving its buffer before GET; the caller releases it before requesting another. A frame is at most 4 MiB, a record at most 1 MiB, and a frame contains at most 1,024 records; these are internal journal bounds, not a revised public API contract. Resolving one uncertain writer position needs one additional read buffer of at most 4 MiB; record-offset tables and provider transport buffers add bounded overhead. These component limits do not establish a process-wide RSS or tenant admission bound.

Discovery consumes frames in order through a four-GET window after its initial epoch probe. The window includes the caller-held frame and bounds payload to 16 MiB per active discovery reader; selected replay retains its one-frame/4 MiB bound. Speculative absence is rechecked when it reaches the front. A hole, error, cancellation or corrupt frame drops the speculative suffix; no detached prefetch worker survives its reader. Up to three reads beyond the first hole and one fresh confirming GET are possible. The cluster admits at most four acquisitions, so discovery payload is bounded to 64 MiB of scratch in addition to its resident and cache allowances. Transport/allocator overhead and whole-process RSS still require qualification. Discovery stops at the first fresh missing position. That result is provisional until the ownership controller durably selects it after ending old acknowledgement permission. Replay of a selected prefix requires every frame and the exact terminal digest, and never extends the prefix when late uploads appear. Provider errors and corruption fail closed.

The journal reports durability, not transaction success or serving permission. It does not implement ownership, seal publication, transaction evaluation, admission or collection. Those remain controller/engine obligations. The earlier handoff models preceded this component. Journal.tla now models durability knowledge and ordered consumption as well as recovery; its unbounded abstract proof assumes an external end to old acknowledgement permission and atomic prefix selection. RevocableOwner explores a timing-independent realization of that boundary. Executing the journal does not establish the complete serving protocol or adopt a clock dependency.

The B2 and S3 bindings now return the same providers::Connection without initializing the publication engine. It exposes measured object operations and the conditional metadata register separately. The journal can write and recover through these transports before any database format is initialized; the existing engine is an explicit consumer through into_published. Raw object CAS is not part of the portable B2 contract, and a metadata observation is not serving permission. A repeated provider check recovered 512 records on each backend, resolved three lost replies and excluded a late suffix; its batch paths made zero authority calls. The S3 run used versioned MinIO, not AWS. The fixture still explicitly uses the existing publication engine to persist its prefix selection.

Handoff fixes an exact old prefix#

A successor must:

  1. Revoke the old incarnation’s permit. No newly issued validation may succeed; already sealed groups with earlier successful validation may finish, and their durable prefixes must be recovered.
  2. Recover the old log’s contiguous durable prefix. Deterministic epoch/sequence names permit ordered point reads; discovery need not rely on one atomic snapshot of a paginated listing.
  3. Durably publish an immutable handoff decision containing that exact prefix before serving or appending a successor epoch.
  4. On restart, recover the existing decision. Never extend an already accepted old prefix merely because another old upload appeared later.

A late upload beyond the sealed prefix is unacknowledged garbage. Including it opportunistically after new work has begun could change the history underneath the replacement. An old upload included before the decision may represent a pending operation with a lost response; normal request-identity recovery must resolve that uncertainty.

The journal proof establishes prefix durability, acknowledgement preservation and selection immutability under the controller/provider contracts. Root recovery and delegated recovery then compose these rules with repeated ownership changes. A journal belongs to a writer generation, independently of the coordinator’s epoch: a surviving writer may continue under a new coordinator, while a replacement writer must use a fresh generation. The composed abstract proofs do not yet establish wire uncertainty, platform timing, transactions, admission or the Rust controller.

The model assumes fresh per-key reads: a negative result must not conceal an upload completed before that read began. AWS documents strong object read-after-write consistency; the B2 visibility contract is described below. Transport errors and unresolved responses must never count as end-of-log. The provider experiments exercise successful reconnect/read/list behavior and journal replay; they cannot prove the provider’s consistency contract or the absence of stale negative reads in every failure mode.

The provider control interface now stamps a fresh mutation identity on every conditional replacement, using the same code for B2 and S3. This handles B2’s identical-metadata no-op behavior at the provider boundary. It does not turn raw observations into serving permission; responses still require fresh permit validation. See the contract and qualification.

The recovery scan requires a narrower freshness contract than a general metadata read: after an immutable upload succeeds, a later point read must find those exact bytes or report an error, rather than incorrectly reporting absence. Backblaze describes confirmed uploads as immediately visible in its storage architecture explanation, and its file documentation says uploads can be downloaded immediately. We rely on that object-visibility contract for direct, uncached journal discovery reads. Selected-prefix catalog pages and records may reuse authenticated bytes from the existing bounded cache; neither cached metadata nor replay grants serving permission. This object-visibility contract does not establish fresh bucket metadata, atomic multi-object snapshots, external CDN behavior or cross-region replica freshness. An uncertain upload may still arrive after a scan; the selected-prefix protocol handles that case separately.

Serving authority remains the central decision#

The first production release must work on the existing Kubernetes hosts. The cloud CLI uses the revocable permits above; platform timing is no longer the selected implementation path. These restricted-profile findings remain fallback evidence, not a deployment requirement.

Keep the restricted-profile findings as evidence, not a deployment escape hatch. The VM qualification rejects unguarded pauses, restored memory and short suspend; a custom no-sleep guest passes a narrower finite test. VMClock prerequisites are absent on the current hosts. The ClockBound experiment finds trusted, nondecreasing timestamps outside the reported interval after stock-guest suspend. None qualifies generic VM leases.

To reopen the clock fallback would require a documented conservative source/error contract, calibrated timestamp/rate bounds available inside containers, disruption and generation detection before restored execution, and a two-host migration/suspend campaign. A direct VMClock binding would require coherent v1 calibration and generation fields, valid maximum-error flags and a supported counter on both hosts. Device presence or ordinary NTP estimates are insufficient. The existing scripts, pinned source hashes, observations and abstract timing proofs remain in the verification record; no production clock or restricted profile is selected.

Root controller and bootstrap#

src/ownership/root.rs connects the common conditional provider session to positive, write-once permits. A fresh UUID binds once to an observed predecessor and checked successor epoch. A claim persists its registration and permit before sending the captured comparison. A lost permit reply requires exact positive readback; the PUT is never retried. Losing or unknown claims cannot retarget their identity.

After a confirmed claim, activation follows the durable registration chain and physically revokes each predecessor permit before opening recovery. It can stop at the inherited checkpoint’s owner, inclusive: that owner had already completed revocation before publishing the checkpoint. An interrupted claimant is not such a boundary. Revocation must confirm absence; lost/corrupt replies fail closed. Unknown activation is resolved by exact control validation, never by inventing local authority.

The native HTTP adapter prepares consistent reads and contiguous durable results before a fresh uncached permit GET. It releases a sealed group only on matching positive bytes. Root identity alone is a structural admission check, never serving permission. The controller retains the local OS guard instead of creating permits for local directories. PID changes refuse service in both modes.

Remote formats owned-candidate-23 (budgeted) and owned-candidate-23-unbudgeted reject older timed writers. Local format 15 remains compatible. Namespace, epoch, incarnation, phase, catalog and checkpoint remain bound in the same B2-bounded record; reserved former timing fields have fixed encoding values. The clock adapter, interval arithmetic, renewal worker and logical startup clock have been deleted. Owner discovery and single-hop forwarding now reuse that record. The library controller now supplies database mapping and membership-driven election/placement. DNS discovery and the native cloud CLI are integrated; sustained provider qualification and full composition remain open.

Durable journal registration#

A root cannot overwrite its predecessor’s only journal identity and rely on process memory to recover it. Before its conditional claim, the controller persists an immutable registration naming its own journal and the predecessor registration. The comparison and predecessor are captured before the upload. A lost upload response requires a positive exact-byte read; an absent or failed read leaves publication unattempted. Each registration has one PUT attempt. Unknown or losing uploads may remain unreferenced and do not create refund rights.

Cluster acquisition funds credit for its registration and permit before observing the claim target. This avoids invalidating that observation with its own grant. Every upload still spends credit normally; unused rights are volatile, lost replies grant nothing, and concurrent metadata changes still require a fresh claim. Candidates waiting on an owner challenge do not allocate credit. A confirmed grant discards the earlier advisory observation before attempting the claim.

The current format requires this discipline and rejects the earlier unregistered candidate format. The root’s fresh incarnation also names its reserved coordinator journal. take_journal opens that writer only once after activation; it cannot reset an old log’s sequence. A new controller follows the current registration’s immutable parent chain to discover previous journals after all prior controllers have disappeared. Missing, corrupt, wrong-namespace or incompatible registrations fail recovery without advancing its cursor. Records are checksummed and at most 234 bytes; traversal keeps fixed bookkeeping, while callers must bound retained results.

The registration model and tests establish this discovery property. The catalog below adds durable prefix selection. Recovery walks the chain only as far as the checkpoint owner; its I/O grows with uncheckpointed ownership history. The optional native upload ledger charges registrations before their first PUT; registration collection remains open. Those are implementation gates, not properties inferred from the existing publication collector.

Persisted recovery decisions#

The root record carries an immutable catalog identity. Each successful claim inherits the catalog from its compared predecessor. The catalog reuses the existing bounded-page B+tree to map registered journal identities to exact prefixes; it is not limited by the number of metadata fields. Its checksummed header is at most 4 KiB, directory pages at most 64 KiB, and each prefix is 112 bytes.

recovery() starts only after confirmed activation and drain. It returns an owning cursor that can wait for storage outside the controller lock. Previous journals arrive newest first. Existing selections use exact-prefix replay, which cannot include later uploads. An absent index entry permits discovery; a missing or corrupt referenced object is an error, never an absent entry. A completed unselected scan is opaque and bound to the controller that started it.

select_prefix() requires live permission and the same confirmed catalog. Exact revalidation can advance the provider comparison while a scan runs, provided the recovery snapshot is unchanged. The operation captures that comparison before uploading its prefix, copied index path and fresh catalog header. Only successful uploads allow the conditional register mutation. Upload errors leave possible orphans and send no publication. A cancelled or timed-out publication may still apply; the next exact validation or winning claim recovers the canonical decision. A changed catalog requires a fresh recovery snapshot.

replay() reads the complete selected catalog in increasing epoch and frame order. It checks the expected journal count before returning frames, checks canonical consecutive epoch keys while paging, and validates each selected hash chain. A cursor retains at most 64 queued keys and one frame budget, reused between journals. The cursor owns its frame and returns a borrowed view; callers must release that borrow before advancing. Its reader cannot obtain a second allocation slot by crossing a journal boundary. Missing or corrupt history does not advance the failed read or complete recovery. Replay may finish after its owner is revoked: callers must reconstruct a private view and check permission after completion before exposing it. Ordered-replay evidence covers this byte-stream contract.

The native projection consumes these journal recovery decisions; the shared HTTP router applies catalog authorization and final ownership checks. The controller supplies placement. Catalog uploads pass through the same optional native upload ledger; unreachable catalog directory entries/pages share the budget collector, while catalog header collection remains open. The native checkpoint layer below bounds suffix replay and ancestry traversal; earlier journals and the checkpoint-covered prefix are reclaimed by native maintenance; obsolete table data, indexes and manifest nodes are also collected. Registrations and catalog headers remain retained. Callers must still bound concurrent cursors and frames. The catalog model and fault tests state the checked scope.

Transaction records and private recovery#

transactions::record encodes evaluated mutations with their database name and generation, resulting revision, original snapshot revision, request identity and fingerprint. A generation prevents a recreated database name from inheriting an earlier database’s receipts. Mutations are unique and ordered; deletion and an empty value have distinct encodings. Recovery applies these results without rerunning application code or evaluating old reads against newer values.

Each record also fixes the receipt-retention floor. Recovery follows this durable decision instead of choosing a window from its current configuration. The floor cannot regress. Retained matching receipts resolve before snapshot-age checks; a missing receipt from a snapshot below the floor is expired, not proof that the operation failed. The internal format permits a window of up to 65,536 revisions rather than fixing retention at the current HTTP engine’s 128 receipts. This is a bounded format/recovery capability, not a selected production policy or a guarantee that every active database keeps that many receipts in RAM. Request lookup uses an ordered index; eviction follows revision order.

transactions::recovery::restore consumes a fresh complete-history cursor and an unpublished target. It validates contiguous per-database revisions and receipt identities before passing evaluated mutations and the next metadata state to the target. Missing or invalid history, target errors and cancellation discard the private target; an already advanced cursor cannot be used to omit an earlier part of history. Only completed replay returns the target. A target implementation must keep partial state private and install all supplied values and metadata; the trait cannot establish those obligations for an arbitrary implementation.

Records are at most 1 MiB, with 128 mutations, 1,024-byte keys and 64 KiB values. Decoding borrows keys and values from the journal frame and allocates at most 128 views. The native index and owner below supply bounded residency, checkpoint recovery, lifecycle and serving. Component tests cover owner replacement, late uploads, interrupted projection and real S3 HTTP object operations. Verification.

Native value index#

The replacement index is native Rust owned by durable-db, with one transaction journal and no external database dependency.

Use one durable transaction journal. Accepted changes enter a bounded ordered memory view; only the contiguous durable prefix is readable or acknowledged, and every response requires current serving authority. Flush that view into immutable sorted tables with sparse block indexes and checksummed range reads. Point lookups should fetch the relevant blocks, while ordered scans merge bounded cursors. Retain revisioned values and deletion markers needed by supported snapshots. Compaction must preserve visibility before any physical bytes can be reclaimed.

A durable manifest/checkpoint must name the exact table set and replay position. Upload data before publishing its references. Recovery must verify that checkpoint and replay the selected suffix; it cannot rebuild from whatever files a bucket listing happens to return. Cancelled or uncertain uploads retain their physical charges. Snapshot retention, compaction and collection need a shared reference protocol. The native checkpoint layer now publishes this binding for selected history. Live checkpoint scheduling now bounds the recent suffix. Raw checkpoint views are not retention pins: collection protects the current checkpoint and the explicitly retained namespace checkpoint. Serving reads hold the owner’s borrow through their final permission check; an expired owner or a stale raw view must fail closed if referenced objects disappear. The operator can retain one published checkpoint until explicit release and export its databases to independently stored logical archives. Scheduled backups remain open; backup and restore describes the current operator API and its limits.

The existing immutable-object primitive supports objects up to 64 MiB and responses up to 8 MiB. Successful uploads return an opaque reference with a fresh identity, size and SHA-256 digest; unknown uploads return no reference and are not retried. Complete bounded reads verify the digest. The native table reader now verifies block metadata through a separately checksummed index object, then checks each bounded data block against its recorded digest. The provider bindings, journal, replay cursor and transaction validator remain reusable without another database engine.

src/index/table implements the native table format. Records sort by binary key ascending and revision descending, preserving deletions separately from empty values. The sparse index searches both key and revision, including when one key’s versions span blocks. Point lookup reads and validates one candidate block while copying only the winning row; a cursor visits one validated block at a time and emits the latest visible row per key, including tombstones for the merge layer. Failed block reads remain errors and do not advance the cursor. The existing bounded memory/disk cache holds immutable blocks and eligible index objects and refetches corrupt disk entries.

Each build encodes a data object and an index object before overlapping their two fresh PUTs. Both replies must succeed before it returns the 152-byte reference for manifest publication. Cancellation or an uncertain reply can strand either object; both attempts retain their physical charges. Data is limited to 64 MiB, with at most 1,024 blocks, a 64 KiB target and 128 KiB maximum block size. An index is limited to 8 MiB. Internal keys allow 2 KiB to accommodate database/generation prefixes around 1 KiB application keys; values remain at most 64 KiB. These are file/record bounds, not database-count or total database-size limits. Builders retain their output buffers; index metadata, active cursors, cache and concurrent builders still require aggregate admission. The table reader alone supplies no serving authority, flush/checkpoint protocol, compaction or collector. Native table verification.

src/index/merge reads overlapping tables at one snapshot, returning the highest visible revision for each key. It retains tombstones, rejects contradictory rows at the winning revision and fails if any source is unreadable. Ordered scans hold one block and frontier row per source; failed or cancelled reads preserve the pending source for retry. Point reads allow at most eight in-flight requests. The 64-source fan-in is a per-read work bound, not a database-count limit; manifest selection and compaction must keep overlapping runs within that bound. The same merge accepts the native memory cursor as one source and applies identical snapshot/deletion rules. Merge verification.

src/index/recovery::Projection is the bounded native target for selected journal replay. It installs evaluated mutations, revision and retained retry receipts together; the runner discards the entire private target on failure. Rows preserve key/revision history and can be read or flushed into the native table format. Aggregate admission counts database generations, retained versions, key/value bytes, receipt count and receipt payload bytes. Recovering initializes the projection with a lazy immutable checkpoint and replays only the selected suffix. Resident limits apply to recent versions and the complete retained receipt windows of touched databases; checkpoint values and untouched database metadata remain paged. Reaching a resident bound still fails recovery. The live transaction owner uses this same projection. Native recovery verification.

index::recovery::Recovering consumes its private state on each bounded replay step. Cancellation or failure discards the partial projection. Between complete frames it can stage a checkpoint containing database revisions, receipt floors, every retained retry receipt and each key’s latest value or deletion. Root::publish_checkpoint conditionally installs the checkpoint descriptor after its tables and manifest have uploaded only against the staging controller’s unchanged recovery snapshot. Live publication reads its comparison after funding and staging, so their unrelated register changes do not require a separate validation update. The publication CAS confirms that observation; a raw read grants no serving permission. Claims inherit the checkpoint reference. A lost or abandoned publication requires exact revalidation; an old staged checkpoint cannot replace a newer cut or adopt a later collection generation.

Checkpoint tables are shared across database generations. Composite keys separate metadata, receipts indexed by request ID, and user values. A manifest tree with at most 64 children per node records ordered upper key bounds for direct lookup. Construction retains one bounded table chunk and one reference buffer per tree level. Rewrites preserve base group boundaries and split overflows evenly; a buffer briefly holds 65 entries, while encoded nodes remain limited to 64. Fresh bulk construction packs full nodes. This retains unchanged siblings after table insertions or removals without additional provider reads; checkpointing still traverses the base manifest. Recovery validates the selected cut and journal chain, then restores complete receipt windows only for databases touched by the suffix. Reads validate the routed objects they visit. Checkpoint construction reuses unchanged references without reading their table indexes, streams changed tables, and checks manifest counts and opened-table bounds; Snapshot::verify remains an explicit full-image audit under caller-supplied resident limits. It rejects value snapshots older than each checkpointed database revision while retaining the recorded retry window. The registration walk stops at the checkpoint owner; it does not revisit earlier ancestors.

Budgeted namespaces use owned-candidate-23 and refuse older accounting policies; no migration is provided. Local directories retain owned-candidate-15; unbudgeted remote namespaces use owned-candidate-23-unbudgeted. It checkpoints partial recovery and the live writer. The live owner schedules checkpoints after 256 durable frames by default, or earlier under resident pressure. Admission drains the upload queue before publication and rebases onto the immutable image afterward. Takeover discovers from the authenticated checkpoint cut before selecting the final suffix. The shared HTTP router serves the recovered native owner. The native maintenance loop reclaims the published checkpoint’s covered journal prefix and earlier ownership journals, including late arrivals outside their selected ends. Recovery must use the current authority’s checkpoint; raw journal cursors do not pin historical data. Checkpoint descriptors are stored directly in the authority record. Collection lists at most 128 table objects, removes the current and explicitly retained checkpoints’ reachable references using the existing bounded manifest walker, and advances a persisted collection generation before deleting the remainder. Staging captures that generation before uploading and rebuilds after any intervening table deletion fence. Scheduled and tenant-isolated retention remain open; the native operator API provides one explicitly released namespace backup slot. Checkpoint creation itself never deletes old objects. Checkpoint verification.

checkpoint::Snapshot::new constructs a view from the inline descriptor without object I/O, then seeks through manifest upper bounds for a requested database generation, key or receipt. Its database handle records the checkpoint revision and receipt floor without loading values or the receipt window. A range cursor retains one table index and one data block at a time, plus bounded manifest traversal state. Failure or cancellation retires that cursor, so interrupted pages cannot be skipped. Immutable manifest nodes, indexes and blocks share the bounded memory/disk cache; the cache does not hold mutable authority. Entries above the cache’s 512 KiB item limit are read with the existing object/range bounds and are not cached. These APIs expose the immutable checkpoint only. Projection::view combines it with the selected recent memory layer for point/range reads at or after the checkpoint revision. A visible recent row, including a deletion, answers a point lookup without reading the older base. Ordered scans merge one checkpoint cursor with one memory cursor. The live owner supplies journal publication and final permission checks. Catalog-backed authorization wraps these reads; the namespace backup slot protects an explicitly retained checkpoint during operator export. Release must remain coordinated with retained readers. Lazy-read verification.

transactions::live groups evaluated transactions into immutable journal frames, checks conflicts against accepted predecessors and serves only the contiguous durable view. Its opaque tickets also defer conflicts that depend on pending writes. Reads and outcomes check ownership after preparing their result. The public read evaluator supports multi-key reads and forward/reverse pages; the commit evaluator groups bounded wire requests with durable retry identities. Protected creation and policy changes are catalog rows in the same journal/index. Catalog lookups bind public names to durable generations; pending revocation blocks new writes and committed revocation also denies old receipt replies. The superseded logical-file namespace has been removed. Live transaction verification.

What the provider measurements establish#

The bounded experiment uses the existing Rust provider bindings, two warmup objects, 32 measured operations per phase, 1 KiB and 64 KiB values, and concurrency 1, 4 and 16. Both B2 and a versioned MinIO fixture verify all 194 objects after reconnecting and match their ordered listing. Measured data operations add zero authority reads, conditional authority replacements or read barriers. Both dedicated buckets are removed afterward.

B2 64 KiB immutable uploads Median p95 Successful objects/second
Concurrency 1 267.9 ms 753.8 ms 3.57
Concurrency 4 347.2 ms 623.9 ms 10.30
Concurrency 16 387.7 ms 1,100.5 ms 23.67

These are raw object operations from the development host to B2 us-west-002, not database transactions or a regional production SLO. Thirty-two samples do not establish tail behavior. Larger concurrency raises throughput while increasing latency in this run. The raw evidence retains every latency and failure count, including the loopback MinIO results; MinIO is not AWS qualification.

This demonstrates useful provider concurrency and supports investigating batched independent publication. It does not establish the throughput of a replacement database. For a lightly loaded database, an individual durable write still waits for object storage; Rust and batching cannot remove that floor. Current native warm reads still require a fresh permit GET, although they avoid the bucket-wide conditional update. Its latency and response grouping must meet the declared workload targets.

Qualification scope#

The controller, DNS membership, resident budgets and cloud CLI are integrated. Bounded B2 campaigns exercise independent databases, stale-owner return, scaling down to one and recovery after total API loss; results retain missed latency targets. Existing tests cover administrator refill under exhausted owner admission. AWS, sustained performance and broader physical-failure qualification are deferred beyond the 1.0 scope.

The bounded registration/acquisition and response models remain component arguments. Repeated takeover, abandoned control calls and concurrent collection still need composed reasoning and adversarial implementation checks. The 1.0 scope records the supported access/resource bounds and manual recovery path, plus deferred tenant fairness, long-duration growth and backup orchestration.

Reproduce the raw provider experiment#

Use the normal kache toolchain configuration and an explicitly dedicated disposable bucket whose name starts with durable-db-test-. Set the existing B2 or S3 credential environment privately, then:

export DURABLE_DB_DISPOSABLE=1
export DURABLE_DB_TEST_PROVIDER=b2 # or s3
export DURABLE_DB_TEST_BUCKET=durable-db-test-UNIQUE
export DURABLE_DB_TEST_CONTEXT='Describe client placement and provider region'
export DURABLE_DB_PROVIDER_FLOOR_REPORT="$PWD/provider-floor.json"
cargo test --locked --test provider_floor -- --ignored --nocapture

The experiment caps immutable data PUTs at 194 and their payload at 6,391,808 bytes. Provider initialization, reads, listing, verification and caller cleanup are additional operations. It writes partial reports between phases and never logs provider error bodies or credentials. The caller must remove the dedicated bucket and all physical versions after either success or failure. The checked-in record includes the cleanup results for both actual runs.
